A zero-variance PPR vector contributes a zero correction. B.2 SEARCH LOOP POLICY Single-query retrieval. LeanSearch v2 and LEANGRAPHSEARCH share the same query and re- sult interface. Each result contains a declaration name, module, kind, formal signature, and available informal description. The client explicitly specifies whether graph augmentation is enabled, allow- ing both retrieval conditions to use the same serving backend. The proving and reasoning callers retain at most K = 50 declarations from each query, even when graph retrieval uses a larger internal pool. Reasoning-based retrieval. The reasoning controller follows a decompose–retrieve–filter–judge loop (Gao et al., 2026). Given the formal statement and an available informal description, the de- composition model generates queries for definitions, high-level results, and individual proof steps. Duplicate query strings are removed before retrieval. A filtering model selects relevant declarations for each subquery using the target statement and the corresponding step description. A judging model then evaluates whether the resulting premises support the proposed plan. An accepted plan terminates the loop; otherwise, the plan and judge feedback are supplied to the next decomposition call. MathlibMPR retrieval and reasoning-based pre-retrieval for theorem proving use the same four templates, reproduced in Section D.4. After filtering, declarations are identified by their module and fully qualified name and ranked by the sum of their positional discounts: a(d) = X u∈Q: d∈Fu 1 log2(rankFu(d) + 1), (8) where Fu is the filtered list for subquery u and ranks start at one. The highest-scoring declarations form the final reasoning context. The multi-branch controller runs independent plans concurrently and uses the first branch accepted by the judge. If no branch is accepted, it pools the final filtered lists from the completed branches and applies the same aggregation rule. Integration with proof refinement. In Standard Mode, the first proof attempt receives no re- trieved context. After a failed attempt, a query generator uses the target statement, current candi- date, and Lean diagnostic to request supporting declarations. The reported proving setup requests five queries per retrieval action and retains up to 50 declarations per query. The five lists contain at most 250 entries and are deduplicated in first-seen order before being supplied to the prover. Retrieved entries are formatted as Lean declarations with their informal descriptions. Reasoning-based proving first obtains an initial context through the reasoning controller. The re- ported Reasoning Mode uses the adaptive policy: the initial proof sketch and retrieved premises are supplied to the prover, and subsequent failures can trigger the same reflection-time queries used in Standard Mode. The initial premises are combined with newly retrieved declarations after failures. The fixed-context reasoning/graph reasoning paths also exist in the codebase, but the re- ported adaptive policy corresponds to their adaptive variants.
