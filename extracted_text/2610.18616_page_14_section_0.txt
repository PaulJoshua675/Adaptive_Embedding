A Knowledge Graph Export We export each of the three STaRK knowl- edge graphs once from the graph data re- leased with the benchmark (Hugging Face dataset snap-stanford/stark, revision 88269e2), using a script that makes no model calls. For Ama- zon, we use the default graph, which includes brand, category and color nodes. STaRK built these graphs from Amazon product reviews and metadata (He and McAuley, 2016; McAuley et al., 2015) together with Amazon question-answer data (McAuley and Yang, 2016), from the Mi- crosoft Academic Graph (Sinha et al., 2015; Wang et al., 2020) through the OGB datasets ogbn-mag and ogbn-papers100M (Hu et al., 2020), and from PrimeKG (Chandak et al., 2023). Each exported graph consists of four parts. Node files. Each node is stored as one JSON line with four fields: node_id (the benchmark ID, which is also the answer ID), node_type, is_candidate and attributes. The attributes field contains all source attributes of the node unchanged, except that non-finite numbers are written as null. Nodes are stored in ID order in shards of 10,000 nodes each (nodes/NNNN.jsonl). Edge files. The edges of each relation type are stored in one tab-separated file, edges/RR.tsv, where RR is the relation-type ID. Each file has a header row (source_id, target_id) and one row for every edge stored in the benchmark’s edge in- dex. Schema and candidates. schema.json lists the dataset name, the node and candidate counts, the node and relation types, the number of stored rows per relation type, the shard size and short notes on the graph semantics. candidate_ids.txt lists the IDs that may be returned: products (Amazon), papers (MAG) and all nodes (Prime). Format description. DATA_FORMAT.txt is identi- cal for the three datasets. In the box below and in every other prompt or file box of the appendices, the text is reproduced exactly, line by line. A line that is too long for the box is wrapped at a space and continues on indented lines. Boxes with a dark blue title contain text that we send to the model. Boxes with a gray title contain files of the graph directory, text produced by the harness or, in Ap- pendix I, the request and gold answers of a case. Boxes with a green or red title contain trajectory excerpts (Appendix I). DATA_FORMAT.txt reads: DATA_FORMAT.txt (Amazon, MAG, Prime) Node records: nodes/NNNN.jsonl, shard number = node_id // 10000. Each line has node_id (benchmark ID), node_type, is_candidate, and full attributes. IDs inside attributes can be external source IDs; return node_id in predictions. Graph edges: edges/RR.tsv, source_id and target_id columns with a header. RR is the relation type ID from schema.json. Stored edge rows are not truncated. For adjacency, inspect either endpoint; the official default graph is undirected. Preserve relation meaning when interpreting directions or entity roles. Only IDs in candidate_ids.txt are valid retrieval outputs. Other nodes are usable evidence. Use shell tools or Python's json/csv modules to read these files. The prompts tell the agent to read this file and schema.json (Appendix B). Shell only and the runs with the rg prompt omit the last line of this file, and No edges omits the four lines about edges (Appendices B.1 and C). What the export preserves. The exported graphs keep all nodes, including the evidence nodes out- side the candidate set (for example, brands in Ama- zon and authors in MAG), with all their attributes, every stored edge row and the type labels. The ex- port is a plain-text copy of the released graph, with the node types, relation types and attribute fields of the release, and predictions are scored directly on the benchmark IDs. After exporting, the script checks that the node files contain every node ex- actly once and in ID order, and that 100 randomly chosen records per dataset read back identical to the source. Queries and gold answers are kept in files outside the agent’s sandbox. Table 4 gives the sizes of the exported graphs.
