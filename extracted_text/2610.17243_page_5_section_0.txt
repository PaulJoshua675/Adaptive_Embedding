4.3 Selected-resource QA The selected-resource path accepts indexes of configured sources, fetches only those sources, processes and stores relevant documents, and delegates answering to database QA constrained to the newly stored identifiers. It there- fore combines controlled acquisition with the consistent retrieval semantics of the central corpus. 4.4 Answer synthesis and graceful degra- dation When a language-model API key is configured, evidence blocks are sent to the selected model with an instruction to answer only from the supplied evidence and to cite bracketed source numbers. When no model is available, or when synthesis fails, the backend returns an extractive evi- dence summary. The fallback is important architecturally: collection, semantic analysis, persistence, retrieval, and inspectable evidence remain available without external model access. The language model is intentionally placed after re- trieval rather than inside the semantic extractors. This limits its authority to presentation and synthesis, pre- serves deterministic structured annotations, and supports independent evaluation of retrieval quality and answer faithfulness. 5 Relationship to the Original EneMonIE Design The original EneMonIE proposal [Küçük, 2022] defines the conceptual foundation, while the present architecture in- troduces the concrete implementation choices summarized in Table 2. The table distinguishes retained, concretized, and newly introduced elements. The new architecture pre- serves the semantic intent of EneMonIE while narrowing its boundary to reusable backend services. The exclusion of the application layer is not a reduction of semantic functionality. It is a boundary decision. The original retrieval and visualization goals can be imple- mented by one or more downstream consumers, while the backend remains testable without an HTTP server or graphical environment. 6 Implementation and Verification 6.1 Reference implementation The prototype is implemented in Python and organized around four main packages: ingestion, processing, ques- tion answering, and resources. The EneMonIEPipeline class composes these packages and owns the central database. Lightweight data classes define documents, enti- ties, temporal expressions, events, sentiment results, pro- cessed documents, and clusters. Configuration is loaded from YAML, making sources and thresholds deployment- specific. 6.2 Preliminary Evaluation: Methodol- ogy and Results An offline evaluation assessed relevance filtering, informa- tion extraction, evidence retrieval, and local processing latency. The experiment used a small synthetic fixture to verify implementation behavior; it does not constitute a representative benchmark of real-world energy informa- tion extraction. Dataset and protocol. The evaluation comprised seven English energy-relevant documents: six news-style records and one social-media record. Reference annota- tions covered ten entity mentions, seven sentence-event- type pairs, and five temporal expressions. The question set comprised six questions: five with annotated relevant documents and one deliberately unanswerable question. The relevance threshold was fixed at 1.5, and tempo- ral interpretation used a reference clock of 22 Septem- ber 2026 at 00:00:00. Evaluation used a temporary SQLite database, with document creation timestamps fixed according to input order. No network acquisition or language-model synthesis was invoked. Component evaluation applied the extractors directly to the reference- relevant documents, while pipeline evaluation assessed outputs after relevance filtering. Metrics. Precision, recall, and F1 were calculated from pooled true-positive, false-positive, and false-negative counts. Entity matching required the exact character span and entity type; event matching required the document, sentence, and event type; temporal detection required the exact span. Normalized-date accuracy measured calendar- date agreement among correctly matched temporal spans. Retrieval recall@5 measured the fraction of annotated relevant documents returned within the first five results for each question. MRR@5 measured the reciprocal rank of the first relevant result, assigning zero when none was retrieved. Both metrics were averaged over the five answerable questions.
