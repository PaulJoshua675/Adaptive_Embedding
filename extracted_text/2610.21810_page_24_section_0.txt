G Storage Format and Systems Measurements End-to-end serving runs and the unfused lookup controls use one node with 8 H200 GPUs, two Xeon Platinum 8462Y+ CPUs, 2 TB of DRAM and 6 local PM1733a NVMe drives in RAID-0. Each H200 has 141 GB of HBM nominally; nvidia-smi reports 143,771 MiB, or 150.8 ×109 bytes. Peak GPU memory in Section 5 and Table 23 is Py- Torch’s max_memory_allocated in units of 109 bytes, taken on the GPU with the largest value. It counts allocated tensors only, not memory the allocator has reserved but not handed out. G.1 Records and lookup kernels Each CP row is a fixed-size record. The record holds the trellis bitstream of the row and one bf16 scale αi (Section 3). A b-bit code on a d-value row takes bd/8 bytes, and the scale adds 2 bytes. The rate is therefore b + 16/d bpp. For DeepSeek at b = 2 and d = 256, a record is 64 + 2 = 66 B, or 2.06 bpp. For Qwen at d = 160, it is 40 + 2 = 42 B, or 2.10 bpp. On SSD the records are aligned so that no record crosses a 4 KB page, and one row is one read. Table 24 compares lookup layouts on DeepSeek. The fused comparison uses one H200 on a four- GPU node with Xeon Platinum 8462Y+ CPUs, Py- Torch 2.14.1+cu130 and Triton 3.8.0. CPU execu- tion and host allocations are bound to NUMA node 0; GPU clocks are not locked. The full 768,022,850- row tables use real CP codes and random tile pay- loads, with the same real row scales and decoder lookup table. Each kernel passes bit-exact checks against its own reference decoder on 8,192 rows, including table boundaries; the two layouts are not matched for output KL. Lookup requests come from the DeepSeek- tokenized first 30,000 documents of held-out FineWeb-Edu shard 001. We test prefill lengths of 1,024, 4,096 and 16,384 tokens and decode batches of 1 and 64, using five independent pro- cesses per placement. Each workload has 20 warm- up requests and 100 timed requests per method; identical requests are paired across methods with alternating execution order. Different runs use dif- ferent request seeds, so between-run variation in- cludes both execution and input variation. Timing uses a host clock with GPU synchronization be- fore and after each call, including output allocation but excluding data loading and request transfer. No cache flush is used. We report the mean and sam- ple standard deviation of the five run medians, not statistics treating all 500 calls as independent runs. At 4,096 tokens, CP and tile windows take 0.1905±0.0034 and 0.2210±0.0034 ms in HBM, and 6.544±0.022 and 10.781±0.091 ms from host DRAM. The per-run tile-window/CP time ratios average 1.160 ± 0.003 and 1.648 ± 0.017, respec- tively. Randomizing the CP code payload while preserving scales gives ratios of 1.163 ± 0.003 and 1.674 ± 0.031 under the same protocol, retaining the direction and approximate size of the prefill advantage. All 20 processes across both payload conditions and placements pass correctness checks, with 20,000 timed calls in total. HBM decode differ- ences are small, and the batch-64 ordering reverses in one of five runs with real CP codes; we do not claim a consistent HBM decode advantage.
