D.2 Decoder-call budgets and actual consumption The main budgets are T ∈{4, 8, 16, 32, 64, 128, 256}. For TIPS, these are exact horizons: each example consumes all T calls, including deterministic finalization, even if an intermediate canvas is already fully visible. Full-canvas decoding uses T −1 learned transitions and one finalization; two-block decoding uses T −2 learned transitions and two finalizations. For example, the two-block policy still makes two learned transitions at T = 4. The horizontal coordinate in the main comparison denotes a decoder-call cap, not necessarily the number of calls consumed by an adaptive baseline. The displayed 8×32 Fast-dLLM configuration uses the mean-adjusted confidence threshold to match budget in expectation (refer to appendix A.2). Other naturally terminating decoding can consume fewer calls than its cap. We therefore distinguish capped accuracy comparisons from measurements plotted against mean actual decoder calls. Controller evaluations and numerical calibration do not add decoder calls, although their runtime is not represented by this metric. Equal decoder-call counts alone do not imply equal wall-clock time or floating-point operation counts across response geometries. D.3 Output processing and answer verification For the main TIPS evaluation, we decode the complete 256-token response canvas with skip_special_- tokens=True, without an additional stop-string truncation. GSM8K reference targets are converted to finite numerical values, using the final #### target when a full dataset answer is supplied. MATH targets are normalized with the mathematical-answer parser, which extracts an answer from boxed, framed, or answer-tagged reference text when applicable. Generated responses are evaluated by the corresponding task-specific extraction and correctness functions. Each verification has a five-second timeout. Missing or nonfinite predictions, answer mismatches, timeouts, and verifier exceptions count as incorrect; they are not removed from the evaluation denominator.
