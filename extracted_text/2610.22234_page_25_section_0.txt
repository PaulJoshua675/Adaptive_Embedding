Each judge accumulates a rubric-based score over fine-grained completion items with assigned weights. It returns a value in [0, 1], with zero for no satisfied items and one for complete satisfaction; if execution raises an exception, it returns the score accumulated before the exception. The evaluator relies only on VM-resident artifacts and deterministic rules, without ex- ternal or cloud-hosted golden assets, and checks the final artifact’s content, structure, formatting, metadata, or configuration state. When deterministic rules fully express the success conditions, the evaluator sets need rule judge=true without enabling visual judgment. When visual layout, canvas state, unparsable application-internal state, or dynamic web content is indispensable for verification, it may set need vlm judge=true. In this case, the VLM judge receives the agent’s execution trajectory as input, and vlm desc specifies the visual objects, attributes, and spatial relations to inspect in that trajectory. Rule-based and VLM-based judgments may both be used for task verification, but their scores are recorded separately. For a task with multiple rule judges, the rule-based score is the mean of the individual rule-judge scores, whereas the VLM-based score is produced independently by visual judgment. During SFT filtering, the two scores are thresholded separately, and a task is retained only when both its rule-based score and VLM-based score meet their respective thresholds (both 0.8). As described in Section 4.1, RL uses only tasks with rule-based evaluators to provide reward signals. This design avoids the brittleness and computational cost of VLM judgment and prevents the calibration mismatch that could arise from averaging the two score types directly. Although both scores lie in [0, 1], rule-based scores are derived from fine-grained, explicitly weighted completion items, whereas VLM scores generally reflect a coarser and more subjective judgment scale. The two scores therefore do not have interchangeable numerical semantics. Consequently, VLM judgment is used primarily to cover programmatic observability gaps during SFT-stage filtering. Instruction and evaluator filtering. Filtering first checks whether the JSON schema, getter ar- guments, and Python code can be parsed and compiled statically. The system then initializes the environment from the initialization configuration and executes the evaluator before any action. The initial-state score must be zero, as a nonzero score indicates reward leakage. An independent review model next scores instruction quality and evaluator quality separately. The former assesses whether the instruction is unambiguous, reachable, and realistic, while the latter assesses whether the eval- uator covers all success conditions, is sufficiently strict, and resists reward hacking. An instruction below the quality threshold is removed directly. If the instruction is valid but its evaluator fails an automated check or quality review, the system uses the previous evaluator and its failure information as revision context, regenerates the evaluator, and repeats the full validation and scoring procedure. The associated proposal is removed only after multiple repair attempts remain unsuccessful. After correctness filtering, we use embedding similarity to remove near-duplicate instructions gen- erated across batches, producing the task pool used for training stages. The RL task pool is then built by rolling out trajectories with the SFT-trained model on this pool and keeping tasks of moderate difficulty. Prototype cross-application extension. Beyond the application–system compositions in the pri- mary task pool, we implemented and began collecting a more structured form of cross-application task synthesis. The prototype uses the related app field in the application configurations to con- struct an application graph. Applications serve as nodes, while edges encode compositional relations induced by shared artifact types or file formats, convertible intermediate artifacts, or complementary workflows. This graph provides a structured prior for composing applications rather than treating all application combinations as equally plausible. For each task, the system first specifies a target number of applications, such as three, randomly samples a primary application, and then samples subsequent applications from its neighboring nodes. After each selection, the neighbors of the se- lected nodes are added to the candidate frontier, allowing the application set to expand along graph structure. To prevent the graph from overly constraining the composition space, each sampling step retains a small-probability jump mechanism that ignores graph connectivity and samples an applica- tion uniformly from the broader inventory.
