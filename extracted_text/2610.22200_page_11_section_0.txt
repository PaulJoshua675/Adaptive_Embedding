3.1.3 Limits of Visual-Only Feedback Result-dependent control is harder when interface observations are limited to screenshots. Conditions such as whether a button is enabled or an input field contains the expected value are not directly exposed as program-readable values, so checking them may require another model call. Accessibility trees can expose text and control states as structured data, allowing programs to query supported interface properties and use them in loops and conditional logic. This motivates combining visual observation with accessibility-tree access in our real-device harness design. 3.2 Harness-to-Model Decision Transfer Code execution addresses how to act by allowing the model to express computer operations as programs. A GCUA must also decide what to observe and how to organize its work. We study harness-to-model decision transfer: replacing selected fixed harness rules with task-dependent model decisions. A screenshot, for example, may be necessary after a GUI action but redundant when program output already answers the relevant question. Deciding whether to request it should depend on the information needed to continue. Mechanism in the Harness, Decision in the Model. As models become more capable, we envision progressively shifting selected workflow decisions from fixed harness rules to the model. The harness should provide reliable mechanisms, while the model decides when and how to use them based on the task and available evidence. In the current implementation, screenshot requests and task-state updates are model-initiated workflow operations, complemented by model-generated action-intent annotations. The harness continues to execute interface calls, preserve task records, and manage context retention. 3.2.1 Mechanisms for Harness-to-Model Decision Transfer On-Demand Observation. The screenshot function lets the model decide whether its next input needs a new screenshot. It can request visual feedback after a GUI action or continue without it when text output is sufficient. On-demand observation can reduce context length by omitting screenshots that add little information. The environment still captures a screenshot after every step, so the mechanism changes what the model receives, not what the environment records. Task-State Tracking. The todo interface lets the model maintain a persistent record of progress, facts, and unresolved questions. It updates this record through todo.update() and retrieves it through todo.list(). Statuses distinguish pending work, attempted changes, unverified changes, and claimed verification, helping the model track what still needs checking. These entries record the model’s assess- ment rather than independently verifying the environment. Action Intent. The intent annotation makes the purpose of each code-execution step explicit. Before each program runs, the model provides a short <intent> block stating what the code is intended to accomplish. A program may combine many operations, making its overall purpose difficult to infer from the code alone. In real-device use, the harness can display this description to users, helping them understand what the agent is trying to do at each step without reading the program. Harness-Managed Context. The harness manages historical tool outputs and screenshots through two fixed policies. A rolling screenshot buffer removes older images in batches, limiting visual context while reducing disruption to prompt caching (Anthropic, 2026a). Micro-compaction applies a similar rolling-buffer policy to textual tool outputs, replacing older outputs with short placeholders in batches while retaining recent results. These retention decisions remain with the harness, complementing the model’s choices about when to obtain new observations and how to track task progress. 11
