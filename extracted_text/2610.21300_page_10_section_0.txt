Experiment 2: pipeline. Six properties fix what each stage does. Con- tent addressing: every document version, extraction, chunk set, embedding set, retrieval result, prompt and raw output is identified by the SHA-256 hash of its content and of the producing component’s manifest, which lists that component’s models, libraries and parameters, not the pipeline’s source code. Determin- istic extraction: the same file yields the same text, including pages read by OCR with a self-hosted model under batch-invariant inference and greedy decoding. Deterministic embedding: for a fixed configuration the same text yields the same chunks and the same vec- tors bit for bit whenever they are computed; within one database, vectors are stored under their content hash and reused. Exact, scoped retrieval: the result depends only on the query and the documents in scope. Serving-invariant judgment: for a fixed engine configuration, the model’s output depends only on the prompt, not on which other requests are served with it, their order, or whether cached prefixes are reused; implemented with batch-invariant inference, greedy decoding and grammar-constrained output. Deterministic records: quotations are verified against the source by rule, unverifiable ones removed and the label downgraded by rule, and every run is written to a hash-chained ledger. The implementation tested is AskDona Assessment, a product of the author’s com- pany (Competing interests). Pages whose text layer has fewer than 200 characters are rendered at 150 dpi and read by olmOCR-2, with GLM-OCR used when olmOCR-2’s output is truncated; chunks of at most 1,400 characters are embedded one at a time with Qwen3-Embedding-8B; retrieval returns the top six of the device’s chunks (4,977 in the main corpus) by BM25 and cosine similarity combined; judgment uses Gemma 4 31B (FP8) on vLLM 0.29.0 with batch invariance; and a quotation that is not found in its cited passage is removed, the label being downgraded to Cannot determine only when no quotation remains (41 quotations and 32 labels in the reference run). Every component, version, parameter, rule and hash is listed in Supplementary Table S15. Judging the 776 pairs took 20.3 minutes with eight concurrent items. Experiment 2: operations. Each run starts from an empty database, re-reads every OCR page and re-embeds every chunk, and records a hash at every stage; judgment-only reruns reuse the reference database’s chunks and vec- tors. The operations were: T1, a repeat from fresh databases, also on a later day; T2, ingestion killed after 131 files and, separately, after 3 files dur- ing OCR, then resumed, judgment killed and rerun, and the inference server killed 90 seconds into judg- ment and restarted before the rerun; T3, sorted, reverse and hash order; T4, 1, 4 and 16 concur- rent documents and 1, 8 and 16 concurrent items; T5, a document added, assessed with the retrieval scope set to the whole corpus, and deleted; T6, the same GPU model on another machine; T7, an H100 80GB (an A100 could not run the configura- tion), run on 4 October and again on 14 October on a second H100 machine created from a disk image of the reference machine, with the GPU mem- ory share raised to give the same absolute memory; T8, judgment rerun with the prefill chunk budget (max-num-batched-tokens) changed from 16,600 to 4,096 (twice with 8 concurrent items, once each with 1 and 16) and to 16,384 tokens; T9, judgment rerun with prefix caching disabled.
