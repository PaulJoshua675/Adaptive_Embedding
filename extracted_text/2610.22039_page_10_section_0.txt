A Construction Pipeline Details This appendix details the three stages of the WEAVE con- struction pipeline introduced in the main paper: typed change loci extraction (§A.1), edge filtering and bounded DAG as- sembly (§A.2), and rollback construction with test attribution (§A.3). A.1 Typed Change Loci Extraction Recovering dependency structure from PR histories requires a representation granular enough to distinguish genuine en- gineering dependencies from coincidental co-modification. File-level overlap—the most common proxy in prior work— conflates distinct changes within shared files and over- connects PRs that modify frequently touched configuration manifests, barrel imports, or dependency lockfiles. WEAVE addresses this by representing each PR as a set of typed change loci: fine-grained program entities extracted from its code diff, each annotated with a structural category that deter- mines its evidential role in coupling computation. We define five locus types, each designed to capture a distinct channel of cross-PR evidence: 1. AST declarations (Last): Function, method, and class definitions identified via language-specific AST parsers. We extract fully qualified names (e.g., module.Class.method) to disambiguate identically named entities across files. 2. Lightweight symbols (Lsym): Exported symbols, type aliases, constants, and enum members extracted from declaration-level analysis without full semantic resolu- tion. This captures entities that do not correspond to func- tion bodies but serve as cross-module interfaces. 3. Configuration and schema entries (Lcfg): Structured keys in YAML, TOML, JSON, and INI configuration files; database migration column definitions; API route declarations; and protobuf/GraphQL field paths. Each entry is represented as a dot-separated key path (e.g., server.http.timeout). 4. Declarations and signatures (Ldecl): Type signatures, interface definitions, abstract method declarations, and trait/protocol requirements. These capture contract-level changes that downstream implementations depend on. 5. Dependency keys (Ldep): Package manager entries (e.g., requirements.txt, package.json, go.mod), import statements, and build-system target declarations. These capture supply-chain relationships between PRs that modify shared external dependencies. Language support. AST parsing is implemented via Tree-sitter grammars, which provide incremental, error-tolerant pars- ing for all six languages. Symbol and declaration extraction build on language-specific Tree-sitter queries; for JavaScript, which lacks a native type system, Ldecl relies on heuris- tic extraction from JSDoc annotations and runtime pat- terns. Exclusion rules. Certain file categories are excluded from loci extraction because they introduce coupling signals unre- lated to engineering dependencies. Test files (matching pat- terns such as test_*, *_test.*, and language-specific test directories) are excluded because test co-modification frequently reflects shared test infrastructure rather than production-code dependency. Generated code, vendored de- pendencies (e.g., vendor/, node_modules/), and bi- nary files are excluded as they represent mechanical artifacts. Formatting-only changes—PRs where all hunks contain only whitespace, comment, or import-order modifications (detected via AST-level diff equivalence)—are excluded to prevent automated formatters from producing spurious cou- pling edges. Deduplication and normalization. Loci are canonical- ized before comparison: fully qualified names are lower- cased for case-insensitive languages (Go exported symbols excepted), trailing version suffixes in dependency keys are stripped, and configuration paths are normalized to dot no- tation regardless of source format.
