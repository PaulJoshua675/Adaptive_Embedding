A Multi-Agent LLM System for Automated Tuning architectural variants. Unlike NAS, the proposed approach uses an LLM, exploits domain knowledge and knowledge of model properties, locally modifies a selected module of an existing network without searching a fixed space of variants, and stores the history of hypotheses in natural language, so that each subsequent iteration can use a substantive analysis of previous iterations rather than only their numerical results. To the authors’ knowledge, the open literature contains no work in which LLM agents are used as a general tool for automatically tuning individual functional blocks of neural network models without redesigning the network itself. MLE-STAR Nam et al. (2026) is the closest agent system; the similarity is limited to two components: logged experiment memory and a sandboxed execution environment. MLE-STAR applies iterative code modifications with an update only when the metric improves on the outer loop, processes the entire ML script, selects the target block with a separate agent, assigns web search to a separate retriever agent, and involves more than ten agents. 3. Method: Multi-agent LLM framework The framework optimizes a selected functional block while keeping the rest of the task pipeline fixed. Before a run, the Human Researcher specifies the task, the block that the agents may modify, the evaluation metric, the software contract for the generated code, and a baseline. These settings allow the same framework to be applied to different problems without changing its architecture or execution loop. The framework is built on top of an OpenAI-compatible API and separates hypothesis generation, software implementation, and experiment documentation into three LLM roles. A sandboxed execution environment and an external experiment log close the iterative loop (Fig. 1). The framework consists of five main components: • LLM Analyst receives the task prompt and the current experiment log. It proposes one hypothesis for the agent-modifiable block and expresses the idea as a technical specification with a fixed structure. If the Human Researcher provides a taxonomy of method classes, the Analyst also assigns the hypothesis to one of these classes. • LLM Coder translates the technical specification into Python code. In addition to implementing the proposed method, the code must satisfy a task-specific software contract that defines the allowed dependencies, class names, call signatures, input and output shapes, and trainable parameters. • Sandboxed execution environment (Docker) inserts the generated module into the fixed task pipeline, first performs a short functional test, and then evaluates a valid candidate. A runtime error is returned to the LLM Coder for correction, whereas the metric from a successful run is passed to the logging stage. • LLM Recorder summarizes the specification, validated code, and evaluation result in a structured JSON record, including the method name, short description, and final hyperparameters. • Experiment log is a table of structured records that serves as the external memory of the framework. Each record is assembled from the outputs of the pipeline stages and contains: – a run identifier assigned by the framework; – the experiment name and a short description generated by the LLM Recorder from the technical specifica- tion and validated code; – the execution status assigned by the control loop from the functional-test and evaluation outcomes; – the resulting target-metric value computed by the task-specific evaluation procedure for a successfully evaluated candidate; – the method class selected by the LLM Analyst when a task-specific taxonomy is used; – the final hyperparameter values extracted by the LLM Recorder from the validated generated code. Records with the With error status remain stored in the complete experiment log. Before the log is included in the Analyst prompt, the framework filters out these records, so the Analyst receives the baseline and successfully evaluated records only.
