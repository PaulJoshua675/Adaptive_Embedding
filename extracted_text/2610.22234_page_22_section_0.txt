B.3 FINAL STATE MATERIALIZATION Our everything-is-a-file abstraction treats the file system as a common inspection interface rather than as a restriction on where a task state must originate. A terminal condition may initially reside in a downloaded web page, an in-memory application state, an unsaved layout, or a persistent user artifact. We attempt to materialize the relevant condition into a VM-resident file representation whenever this can preserve the semantics needed for evaluation: a web state may be downloaded or serialized locally, an in-memory result may be exported, and an answer may be written to a structured or plain-text file. This externalization separates the location of a state from its verifiable representation and allows heterogeneous desktop objectives to share a common evaluation interface. The materialization step is not uniformly lossless. Some conditions, such as exact document struc- ture, metadata, or serialized application state, admit faithful programmatic inspection; others depend on rendered layout, canvas appearance, transient UI state, or content for which serialization does not preserve the relevant evidence. Evaluator selection therefore reflects an observability trade-off: rule-based checks are used when a deterministic file or command representation captures the re- quired semantics, VLM-based checks are used when visual or otherwise non-serializable evidence is essential, and hybrid evaluators combine the two when they provide complementary evidence. The resulting evaluator is agnostic to whether the agent reached the terminal condition through GUI actions, code execution, or their combination. 22
