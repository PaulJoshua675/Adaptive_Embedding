The data engine G generates executable scenes with independently editable task, spatial, and object-attribute factors (τ, σ, α) and a sparse success verifier ν. Construction traces and rollout-grounded failure diagnoses enter a shared memory, which organizes them into reusable difficulty modes. Validated modes are compiled into generation programs that reproduce the diagnosed conditions and training programs that specify subgoals, potentials, and learning tools. Text2potential supplies dense feedback through chunk-level value targets that guide policy updates, and measured learning progress guides the next generation round. that recreate the diagnosed conditions and training pro- grams that help the policy πθ overcome them. We first construct seed environments (§3.1) and de- fine the shared memory (§3.2). Each round then uses the memory to guide scene generation (§3.3), com- piles validated diagnoses into training programs through Text2potential (§3.4), and updates the policy using shaped value estimates (§3.5). The resulting learn- ing progress informs subsequent generation. Figure 2 provides an overview of the overall framework. 3.1. Seeding and Scene Representation Seeding begins with an object pool [5, 33, 51]. We use a task family’s assets when available and otherwise sample from a predefined pool. Given the sampled objects, the engine proposes a task [38] and specifies its instruction, participating objects, initial and terminal object states, and executable success predicate ν. Proposals without a verifier are discarded. Instead of committing to a specific data generation scheme, the engine writes factored scene programs. Task, layout, and object attributes can then be perturbed inde- pendently, letting the loop test a diagnosis by changing one factor while keeping the others fixed. Failure di- agnosis and scene generation need to share a common representation. The critic should identify factors that the engine can directly modify. We parameterize each environment as s = (τ, σ, α), generated by executing a scene program s=Exec(g) with g ∼G(·). The task fac- tor τ specifies the goal predicate, instruction, and initial and terminal object states. The object-spatial factor σ specifies poses, support and containment relations, clear- ances, and occlusion. The object self-attribute factor α specifies geometry, metric scale, mass, friction, articu- lation, and appearance. The SDK exposes these factors through set_task, set_layout, and set_attributes, so the engine can resample any one factor while keep- ing the other two fixed. This factorization provides a common representation for the critic’s diagnoses, the engine’s interventions, and the applicability conditions of compiled generation programs. Verification. Each program emits a sparse, machine- checkable success predicate ν over its scene objects. This predicate determines task success independently of the critic’s judgments and provides the common success criterion across the methods we compare. Dense training feedback is introduced separately through potential-based shaping, rather than replacing the task predicate with a synthesized reward [42, 48]. Before policy deployment, each scene must pass verification checks for collision-free placement, static stability during a short passive simulation, and plausible metric scale. Programs that fail these checks are excluded from policy rollouts but retained in memory to inform subsequent scene generation. 3.2. Shared Heterogeneous Memory Memory combines two sources of experience: the engine’s construction and repair traces, and the pol- icy’s rollout outcomes and failure diagnoses. Follow- ing the episodic–semantic–procedural organization of language-agent memory [30], we retain individual records (episodic tier), abstract recurring failure patterns (semantic tier), and compile reusable programs for gen- eration and training (procedural tier). 3
