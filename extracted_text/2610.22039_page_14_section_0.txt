B.2 Randomized-Graph Controls To confirm that Graph Credit’s diagnostic value arises from the true dependency structure rather than arbitrary graph constraints, we evaluate node-permuted random graphs as controls. Experimental setup. For each WEAVE-Bench task, we generate 10 random permutations of the node labels while preserving the DAG topology. Graph Credit is recomputed under each permuted graph, and results are averaged across permutations. Results. Under the true DAG, the mean OverCredit (Flat- F2P −Graph Credit) is 10.5 pp across all agent configura- tions. Under randomized graphs: • Mean OverCredit drops to 1.6 pp (<2 pp as reported in the main text). • The standard deviation across permutations is 0.7 pp, in- dicating stable behavior. • For 89% of tasks, the randomized OverCredit is within 2 pp of zero. This demonstrates that the gap between Flat-F2P and Graph Credit under the true DAG reflects genuine phantom credit arising from dependency violations, not an artifact of imposing arbitrary graph structure. B.3 Chain-Depth Interpretation Graph depth requires an explicit counting convention. The benchmark summary in Figure 3 and Table 19 counts nodes on the longest path of the full task DAG G. For scoring and curriculum thresholds, depth counts edges; a path containing k nodes has k −1 edges. A single-node graph therefore has edge depth zero. The scoring graph GA is induced by evaluable nodes and can have a shorter longest path than the full task graph. The recursive minimum in Graph Credit caps downstream completion by upstream prerequisites at every edge. Longer chains consequently provide more opportunities for locally passing tests to be capped by an unresolved ancestor. This is a structural property of the scoring rule; it does not by itself establish an empirical relationship between chain depth and OverCredit. The overall OverCredit results are reported in Section 5.2. Software environment. Agent evaluation runs execute in isolated Docker containers. The primary software stack uses Python 3.12 with PyTorch 2.x. Model training employs a distributed training framework supporting ZeRO-3 paral- lelism, sequence parallelism for long-context batches, and mixed-precision (BF16) optimization. For agent evaluation (RQ2), all eight evaluated models are accessed through their official provider endpoints, so that measured behavior re- flects production inference settings. Trajectory generation for WEAVE-Train (§E.1) instead uses a self-hosted deploy- ment of the open-weight generator, which makes the corpus reproducible without dependence on a hosted endpoint. Resource allocation. Each agent evaluation run executes in an isolated container with a 2-hour task-level timeout. SFT and RL training use multi-GPU distributed configura- tions. We report the hyperparameters that determine the op- timization trajectory (§E.2, §E.3) rather than device counts or sharding topology: the former fully specify the training run, while the latter are deployment choices that vary with available hardware and are omitted per organizational policy. Scaffold differences. OpenCode and Cline differ primarily in their system prompts and tool invocation patterns. Open- Code uses a structured XML-based action format with ex- plicit planning steps, while Cline employs a conversational format with implicit planning. Both expose identical underly- ing capabilities (shell execution, file reading/writing, patch submission). The choice of two scaffolds enables assess- ment of scaffold-invariant model capabilities versus scaffold- specific behaviors.
