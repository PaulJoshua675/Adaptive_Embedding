Shared Operations with Explicit Targets. Common operations use a shared vocabulary, while platform adapters implement their native behavior. For example, the macOS adapter uses the unmodified Cua Driver from trycua (trycua, 2026). Each operation is scoped to an explicit resource, such as a device, application, window, or browser tab. Resource handles retain their targets independently, so selecting a new target does not redirect earlier bindings. This gives agent programs a consistent way to address multiple devices and applications without relying on a single implicitly selected target. Cross-Device Coordination within One Task. Within one session, programs can combine observations and actions from multiple resources while reusing host-side variables and bindings across turns. The program executes in the host runtime, whereas device.shell.run executes commands on the selected device where supported. File transfers through mu.files.copy identify both source and destination resources. These mechanisms allow intermediate results from one environment to guide operations in another. As an illustrative workflow, an agent could retrieve a report through a phone application, transfer it to a computer for analysis, and enter the results into a browser-based service, coordinating all three stages within the same task. Shared Observation Processing and Selective Delivery. The SDK exposes ui.ax for structured seman- tic observations and element-based actions, and ui.vision for images and coordinate-based interaction. Semantic state supports programmatic conditions and checks, while vision provides complementary information when semantic observations are insufficient. Adapters normalize native accessibility and browser semantic trees into common representations, allowing filtering and compact rendering to be reused across compatible platforms. Observation capture is separate from delivery to the model. Calls such as ui.ax.observe() return data to the program, while mu.emit delivers selected observations or computed results to the model. A program can therefore inspect multiple targets, use structured results to determine subsequent operations, and return only the information needed for the next model decision. This separation supports cross-device execution without requiring a model call for every intermediate structured observation. Explicit Platform Capabilities. A common interface does not imply identical capabilities across plat- forms. Each resource declares its supported operations and options. Common UI operations and device services share interfaces, while platform-specific features remain explicit through namespaces such as .android, .macos, and .browser. Operations such as Android navigation and browser page evaluation thus retain their own semantics, allowing programs to reuse common interaction patterns while selecting methods appropriate to each target. 4.3 Real-Device Harness The Cross-Device SDK defines the programming interface for device observation and control. The real-device harness integrates this interface with the agent loop, program execution, and platform-specific mechanisms, enabling the model to work on a user’s computer while retaining task state across turns. 4.3.1 Five-Layer Architecture We separate the system into five layers (Figure 9). The model generates a program, the runtime executes it, and SDK calls are translated by the driver into operations on applications and the operating system. Explicit interfaces separate responsibilities and allow compatible components to be replaced indepen- dently. Detectable execution failures are reported where they occur; successful action delivery is not treated as evidence that the intended task-level effect has occurred. Model.
