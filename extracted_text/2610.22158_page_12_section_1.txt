Positive-Sample Metrics. SQL Behavior. Mea- sures the degree of abstention from generating SQL for flawed queries. • 0: generates complete SQL; • 1: partial abstention or invalid SQL output; • 2: complete abstention or explicit refusal. Detection. Measures whether the model recog- nizes the query as flawed. • 0: no detection; • 1: detects flawed premises. Type Identification. Measures whether the model correctly identifies the underlying flaw type. • 0: incorrect type identification; • 1: correct type identification. Type Identification is assigned 0 when Detection = 0; otherwise, it evaluates whether the correspond- ing failure type is correctly identified. Negative-Sample Metrics. SQL Generation. Measures whether the model generates SQL for a negative sample. • 0: does not generate SQL; • 1: generates SQL. GEN is reported as the proportion of negative samples for which SQL is generated and is avail- able in all three prompting settings. Validity Judgment. Measures whether the model explicitly recognizes a negative sample as valid. • 0: does not explicitly judge the query valid; • 1: explicitly judges the query valid through is_valid=true. VAL is reported as the proportion of negative samples explicitly judged valid. It is available only in the Implicit and Explicit prompting settings because the Base output format does not include is_valid. B.3 Automatic Evaluation Prompt We use LLM-based evaluation prompts to assess model behavior on flawed queries. The evaluation focuses on three metrics: SQL Behavior, Detection, and Type Identification. Given a user question, model response, and the ground-truth flaw category, the automatic evaluator determines whether the model: (1) refrains from generating misleading SQL, (2) recognizes that the question is flawed, and (3) correctly identifies the underlying flaw type. We adopt a unified evaluation prompt structure across all error categories, with category-specific definitions and scoring criteria.
