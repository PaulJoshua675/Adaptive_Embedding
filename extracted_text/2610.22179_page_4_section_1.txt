4.1 Bounded exponent codes Coding background. Huffman coding (Huffman, 1952) assigns variable-length prefix-free codewords, with shorter codes for more probable symbols. For a matched source model, its expected length is less than one bit per symbol above entropy, but individual codes can be as long as the alphabet size minus one. Length-limited Huffman coding (Larmore and Hirschberg, 1990) bounds this worst case, and Package-Merge efficiently constructs the optimal code under the length constraint. Escape coding (Vitter, 1987) groups rare symbols under a shared prefix followed by a literal, freeing shorter codes for common symbols. LCT uses bounded Huffman codes with escapes to combine compact storage with simple parallel decoding Arithmetic coding (Witten et al., 1987) and ANS (Duda, 2013) can approach the entropy limit without the integer-length constraint on individual symbols, but are slower to implement on the GPU, as we show in the comparisons. LCT code construction. LCT splits each BF16 value into an exponent byte and an unchanged sign–fraction byte. We write P = (pt) for the centered distribution of exponent symbols in the tensor, and Q = (qt) for the fixed coding model. The user selects Q based on prior knowledge of the tensor distribution. It is not estimated at runtime, avoiding codebook construction during training. At runtime, a sampled exponent center shifts the codebook to adapt to the tensor scale (Section 4.4). The codebooks are precomputed before running and a mismatch between P and Q can increase storage. LCT adopts bounded Huffman coding with escape coding. Prefixes are capped at eight bits and rare escaped symbols are encoded with an escape prefix followed by an eight-bit literal. Without escapes, coding all 256 symbols under this cap would force every code to have length eight. Escapes free short prefixes for common exponents. The codebook construction is based on Package-Merge (Larmore and Hirschberg, 1990). LCT further adapts this algorithm to handle escape values. We sort symbols by probability qt and test every tail cutoff. Package-Merge optimizes prefix lengths for each candidate. The final code minimizes C(D) = X t∈D qtℓQ(t) + qesc (ℓesc + 8) , (1) where D contains directly coded symbols, ℓQ(t) is the length Q assigns to symbol t, ℓesc is the escape-prefix length, and qesc is the escaped tail mass. Algorithm 1 gives the full algorithm, with an optimality proof given in Appendix B.1. 4.2 Storage structure Storage consists of two components. The sign and fraction bits are stored together as uncompressed sign–fraction bytes. The encoded exponents are stored in fixed-size blocks. Each block holds B exponent symbols. The clean and sparse configurations use B = 65,536 and the medium and high configurations use 32,768 (Table 12). Blocks tile the tensor, with padding. Each block is divided into L = 256 streams, independent units that enable parallel encoding and decoding, containing S = B/L symbols at a fixed budget of F bits. The sizes are tuned based on the expected size of the encoded stream. The mapping from tensor positions to streams is cyclic. Consecutive elements land in different streams so streams do not hold a full row or column of a tensor, which may be strongly correlated (e.g. a neuron or batch may output all constant values). A fixed budget cannot cover every stream, because code lengths vary. If a stream’s codes exceed F, LCT writes an overflow tail. The remaining exponents are stored uncompressed. A marker indicates where the tail starts, if any. 4.3 User-selected models and budgets The users have several options to choose from when selecting Q. By specifying the distributions a priori, LCT avoids computing Huffman tables at runtime, improving compression performance, while still being applicable to different scenarios. Distribution. LCT provides a set of default codebook distributions, including a power-law model with an exponential body and a power-law tail, based on Nemotron-H activations. In addition, several other parameters may be specified. A shift parameter allows for distributions shifted by an additive constant. Zero inflation specifies a percentage of the distribution that is set to zero. Together with exponent shifting, these handle the typical distributions encountered during training. The user may specify additional exponent distributions if required in terms of a probability density table. 4
