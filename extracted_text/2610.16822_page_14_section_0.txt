A Additional Experimental Details A.1 Implementation Platform The NAS-Bench-101 and NAS-Bench-201 attribute-prediction experiments are implemented in PyTorch 2.4.0 and conducted on a workstation running Ubuntu 22.04 with an Intel Core i9-13900K CPU, 64 GB RAM, and a single NVIDIA RTX 4090 GPU with 24 GB memory. The large-DAG scalability experiments are conducted separately on an NVIDIA A800-SXM4-80GB GPU, with the corresponding hardware configuration and timing protocol reported in Appendix F. A.2 Datasets, Splits, and Training Budgets NAS-Bench-101 [34] contains 423,624 unique cell-based architectures with at most 7 nodes and 9 edges per cell. NAS-Bench-201 [35] contains 15,625 candidate cells with 4 nodes and 6 edges per cell. For NAS-Bench-201, we represent edge operations as nodes in the predictor input graph, whose encoding topology is fixed across operation assignments. The NAS-Bench-201 authors trained candidate architectures on CIFAR-10 for 200 epochs and recorded their validation accuracies, alongside latency measurements collected with a batch size of 256. These measurements serve as labels for our accuracy and latency prediction tasks, with accuracy averaged over the available benchmark runs for each architecture. NAS-Bench-101 provides accuracy labels but not latency labels; therefore, we measure NAS-Bench-101 latency on an NVIDIA RTX 4090 GPU using batch size 1 to complete the four-task evaluation. Because latency labels are benchmark- and device-specific, latency magnitudes are compared only within the same benchmark setting. For each task and training budget, each method is evaluated over five runs using a shared set of five random seeds. For each seed, architectures are randomly shuffled to form the training and validation partitions. The partitions vary across seeds, and all methods share the same partitions for a given seed. The @ notation in the result tables denotes the number of architectures used for predictor fitting, and the validation set contains 1,024 architectures. Because the predictor serves the candidate screening stage of NAS, its objective is to score and rank the complete architecture pool and identify promising candidates for costly downstream evaluation. We therefore compute Kendall’s τ and MAPE over the full benchmark architecture set, including the training and validation architectures and all remaining candidates. A.3 Fair Comparison and Reproducibility Within each seed, all methods use the same training and validation partitions, full-set evaluation target, training budgets, and metrics. When reproducing baselines, we use the official implementations when available and preserve their original model configurations; otherwise, hyperparameters are selected by grid search within the ranges reported by the corresponding papers. DTA-GT uses one fixed default configuration across tasks and budgets. The main comparison and ablation tables report means over five runs; Appendix H also reports the corresponding standard deviations. A.4 Descriptions of Baselines We compare DTA-GT with representative sequence-, CNN-, GNN-, Transformer-, and hybrid architecture predictors. For methods with public source code, we use the released implementation as the primary reference. For methods for which we did not identify an official public implementation, we reproduce the predictor from the paper description and tune only within the reported or standard ranges under the shared split, budget, and evaluation protocol described above.
