Packed execution reduces HBM footprint but pays decode cost repeatedly; expanded execution spends additional HBM to amortize decoding across subsequent candidate tiles or requests. For 4-bit-average behavior memory KV configuration, packed residency uses approximately 3.1× less behavior memory-state HBM than retaining expanded high-precision KV, with approximately 6% higher behavior memory-kernel latency. In the measured workload, expanded residency becomes preferable after approximately 4–6 reads of the same KV snapshot. The packed-versus-expanded choice is therefore itself an amortization decision: decode repeatedly, or pay the expansion cost once and amortize it over future reads. 5.4.2 Tiered KV Residency Published KV is stored in compressed form in a shared on-disk storage tier and cached opportunistically in host and GPU memory: on-disk KV −→host-resident KV −→GPU-resident KV. Residency is determined by expected KV reuse relative to resident bytes, transfer cost, decode cost, and available memory. Cold KV remains packed in the on-disk store; warmer state may be retained in host memory; and active KV can be admitted to GPU in either packed or expanded form. Importantly, residency and execution format are independent decisions. A packed KV snapshot may move across disk, host, and GPU tiers without changing its logical version, while promotion from packed to expanded GPU residency changes only its local execution representation. The same published KV therefore admits the following operating points: Placement Format Preferred regime Backing store Packed Cold population; minimize storage footprint Host memory Packed Warm state; avoid repeated on-disk store reads GPU memory Packed HBM-constrained or low expected reuse GPU memory Expanded Repeated reads with sufficient HBM KV admission can therefore adapt to access frequency without changing the model interface. A newly fetched snapshot may initially remain packed on GPU and later be promoted to expanded residency if observed or predicted reuse justifies the additional HBM. Conversely, inactive, unpinned KV can be demoted while preserving its compressed on-disk representation. All requests consume only KV compatible with their pinned model and representation version.
