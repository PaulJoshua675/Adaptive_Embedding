CoDA: Co-Evolution of Data Engines and Action Policies A. Transferring Generation Programs Across Task Families A generation program can be reused in a new task family when its object requirements and relational constraints are satisfied in the new scene. We call this transfer lifting. Each program refers to objects by symbolic role, such as target, obstacle, or support, rather than by a specific object instance. Each role specifies a required object category, such as container, or an affordance, such as graspable. The program also specifies the rela- tions required between these roles, such as an obstacle occupying the approach path to the target. To apply a program to a new scene, Rgrind matches these requirements against the scene program’s symbol table, which records object identifiers, categories, affordances, poses, and relations. This information is available di- rectly because the data engine constructs the scene pro- gram. A valid binding assigns each role to a distinct scene object and satisfies all role requirements and relational constraints. If no valid binding exists, the program is not transferred to that scene. Matching is exhaustive: our programs contain at most five roles and our scenes contain a few dozen objects, with matching taking mil- liseconds in this setting. When several bindings are valid, they are ranked first by how closely their object categories match those in the dif- ficulty mode’s previously validated variants. Ties are bro- ken using the margins by which the relational constraints are satisfied. We retain at most three bindings and exe- cute the generation program separately for each, produc- ing a scene variant and its own matched control batch. Transferred programs undergo the same validation as programs learned within the new task family. Their gen- erated variants must pass the scene-validity checks, and policy rollouts evaluate both the targeted variants and their controls. A transferred program enters Ωfor the new family only when the control comparison supports the attributed difficulty and the measured success rates of its variants fall within the success band. Thus, match- ing establishes whether a program is applicable to the new scene; evaluation establishes whether it reproduces a useful training difficulty. B. Implementation Details Environments and evaluation. We construct MuJoCo environments for four task families: pick-and-place, articulated open/close, put-inside, and stack/insert. Each family includes an in-distribution evaluation suite and four held-out suites of 100 environments each, testing generalization to unseen object instances, layouts, tasks, and categories, respectively. Held-out environments never enter M. In a second setting, we initialize the loop with the 30 LIBERO source tasks and evaluate on LIBERO-Pro [52] (Table 2). All results are reported as mean ± standard error over three random seeds. Assets, observations, and actions. The asset collection comprises 1,200 rigid objects from Objaverse across 60 categories, 300 articulated objects from ArtiCraft-10K, and 500 seed layouts from TableVerse [5, 33, 51]. The robot is a 7-DoF Franka Panda with front and wrist cam- eras, each providing 224 × 224 RGB observations. Con- trol runs at 10 Hz using seven-dimensional actions: six dimensions for the change in end-effector pose and one for the gripper command. Each action chunk contains h = 8 control steps. Policy backbones. Our primary policy is π0.5, a 3B- parameter model with a flow-matching action head [8]. We initialize it from the released openpi base checkpoint, or from its LIBERO-fine-tuned checkpoint for the LIBERO experiments [26]. We also evaluate the 7B-parameter OpenVLA-OFT [12] in table 7. Both policies are fine- tuned using LoRA with rank 32 and a learning rate of 10−5. At each rollout decision, the policy samples j = 8 candidate action chunks. These are combined using soft- max weights computed from Qϕ, with temperature 0.5. Scene generation, diagnosis, and potential compi- lation. The data engine, rollout-diagnosis model, and potential compiler all use GPT-5.5 [21]. Planner-certified demonstrations are obtained using cuRobo [31]. The diagnosis model receives rollout video, contact informa- tion, joint states, and the task success verifier’s output at each timestep. It assigns each diagnosed failure to one of four factors (TASK, SPATIAL, ATTRIBUTE, or EXECUTION) and one of five trajectory phases (approach, grasp, transport, place or insert, and release). For potential compilation, Text2potential retrieves three exemplar programs from Φj and uses a library of 12 helper functions. Generated programs undergo at most two rounds of repair for syntax or runtime errors. Value learning and policy optimization. The value critic Qϕ uses frozen DINOv2-B [22] and T5-base [28] encoders followed by a four-layer transformer decoder. It is trained by categorical value regression with 101 bins spanning [−βmmax, 1], where β = 0.5 is the shaping coefficient and mmax = 4 is the maximum number of subgoals. We use a discount factor of γ = 0.99 and an exponential moving average target network with update coefficient τ = 0.005. Each round includes KQ =20,000 critic-update steps with batch size 256 and Kπ = 5,000 policy-update steps with batch size 64. The advantage-weighted policy update uses λ=1. Generation budgets and rollout protocol. Experiments use n = 5 rounds, with per-family budgets of 320 ac- cepted environments, 1,280 planner-certified demonstra- tions, and 2.5M LLM tokens. Token counts include scene generation, diagnosis, and potential compilation. Ex- tended runs use n = 15 rounds. Each round generates B = 64 targeted environments and 64 control environ- ments per task family.
