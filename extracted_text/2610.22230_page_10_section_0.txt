Agentic Kernel Optimization Workflow While GDPA and HSTU are widely shared across models, Meta’s DLRM ecosystem contains a long tail of custom kernels tailored to individual models. Manually tuning each kernel is labor-intensive and does not scale. To address this, we developed an agentic AI workflow that encodes our tuning principles as executable skills, enabling automated kernel performance analysis and optimization. This workflow builds upon Meta’s KernelEvolve framework [47], which provides the underlying agent infrastructure and skill abstraction mechanisms. While KernelEvolve focuses on the general systems architecture for agentic code optimization, our contribution lies in encoding AMD-specific tuning principles as production-ready skills and validating their effectiveness at scale on Meta’s production DLRM training workloads. The agentic workflow operates in three phases: 1) Benchmark & Profile: Capture representative inputs from production workloads, reproduce the performance in a standalone benchmark, and leverage profiler tools (e.g., AMD rocprofv3 [48], Triton Proton [49]) to identify the main bottlenecks such as low occupancy, poor cache utilization, or instruction stalls. 2) Match & Fix: Map observed bottlenecks to a library of optimization skills, each encoding a tuning principle (e.g., PID swizzling, occupancy hints, atomic avoidance) with code transformation templates and applicability conditions. 3) Generate & Validate: Produce candidate kernel modi- fications, benchmark them on representative inputs, and verify numerical equivalence (within tolerance, automatically rejecting failures) and performance improvements on a set of production workloads. Case Study: Jagged Flash Attention. We illustrate the workflow with the jagged flash attention (JFA) kernel, which represents a challenging optimization target due to its ir- regular memory access patterns. The JFA kernel, used in our ranking models, exhibited a 2× slowdown on MI350X compared to B200 in its backward pass. Profiling revealed that tl.atomic_add operations dominate execution time, a known bottleneck on AMD’s multi-XCD architecture (see Section IV-B for details). The agent recognized this pattern, noting that the grouped query attention (GQA) mode causes multiple Q heads to race on shared dK/dV gradients. Following the skill’s guidance, the agent rewrote the kernel to accumulate dK/dV in registers per KV-head group and issue a single tl.store at the end, a tree-reduction pattern that eliminates atomic operations. The optimized kernel achieved a 2.3× speedup (32 ms→14 ms), transforming MI350X from 2× slower than B200 to 15–20% faster, and delivering a 25% improvement in end-to-end model training throughput. Applying to dozens of production Triton kernels within Meta’s DLRM ecosystem yields a success rate exceeding 80%. Agent-generated optimizations achieve near-expert performance while reducing development time by an order of magnitude. For a comprehensive evaluation of the effectiveness across diverse kernel types, we refer readers to [47]. By codifying expert knowledge into reusable skills with clear triggering conditions and transformation patterns, the workflow enables systematic exploration of the optimization space while ensuring that anti-patterns for AMD GPUs are automatically detected and addressed. Generality. Our workflow builds on Meta’s KernelEvolve [47], which encodes tuning expertise as reusable skills across NVIDIA, AMD, and MTIA. The skill abstraction transfers across ISAs. The atomics-to-tree-reduction skill above has a direct analog on Meta’s MTIA accelerators [5, 6], whose PE array also handles contended atomics inefficiently: the same global-atomic reduction is rewritten as a per-PE local reduction followed by a global reduction over the on-chip reduction-engine network, yielding ∼10× (up to 65×) speedups on reduce-style kernels. Because the workflow needs only a portable tile-level kernel DSL and a compiler, which Google TPU (XLA/Pallas) [50] and AWS Trainium (Neuron/NKI) [8] also provide, these skills extend to a new accelerator as an incremental port rather than a from-scratch rebuild.
