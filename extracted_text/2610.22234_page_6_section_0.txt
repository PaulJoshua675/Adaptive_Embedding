Data infrastructure details are provided in Appendix B. 3.3 TRAINING PARADIGM 3.3.1 SFT COLD START Most open-source CUAs used as base models have previously been trained primarily for GUI-only interaction. They may possess visual understanding, coordinate grounding, and low-level control, but have not learned the new decision boundary created when code execution becomes an equally valid action. Merely adding a code tool expands the action space without supplying a routing prior for when to remain in the GUI, when to switch to code, and when to return to the interface for verifi- cation; it can even disrupt already learned GUI behavior. SFT therefore serves as a cold start in our pipeline: it establishes the action semantics of the unified tool schema and distills from teacher tra- jectories a coarse but usable GUI/code routing policy. We collect SFT trajectories on tasks produced by the data infrastructure described in Section 3.2, using Claude Sonnet 4.6 (Anthropic, 2026) as the teacher model with both Computer Use and Bash Tool enabled. The resulting trajectories are then postprocessed and normalized into the OS-Helix action schema. Each trajectory is scored by its eval- uator, using the teacher model itself when visual judgment is required, and the resulting score serves as the primary signal for rejection sampling. We further apply a filtering pipeline to remove mal- formed tool calls, schema-mismatched actions, and trajectories that fail evaluator or quality checks, yielding a set of high-quality SFT samples. Training hyperparameters and data-mixture details are provided in Appendix C.1. 3.3.2 AGENTIC RL WITH STEP-BALANCED GSPO We first build a cross-node environment management system that monitors and manages over one hundred Ubuntu sandbox environments across multiple standalone machines. The system exposes a unified port to the training side and internally dispatches requests to the environments. We then perform online RL on carefully filtered generated tasks with rule-based evaluators only, further improving model performance. Each rollout interacts with a live desktop environment, and the paired evaluator score serves as the sole outcome reward signal. If an assistant turn contains an unparsable tool call or any other invalid action-format error, that assistant response is isolated as an invalid sample and assigned a reward of 0, even if the remaining trajectory could receive a positive evaluator score. We use three efficiency mechanisms to make online RL feasible under costly desktop interaction. First, we adopt an asynchronous RL pipeline that allows the rollout policy to lag behind the latest policy by at most one version, enabling environment interaction and policy optimization to run in parallel. Second, we maintain per-task success-rate estimates and bias sampling toward tasks near the current capability frontier, down-weighting tasks that are already too easy or remain too difficult. Third, we apply bounded sliding-window visual-context segmentation to control context length and sample growth. Rollouts are split into segments and each segment can contain multiple assistant actions that contribute to loss. We apply the same sliding-window segmentation logic during rollout inference to maintain consistency between training and inference. In our preliminary RL experiments, standard GSPO exhibited a systematic drift toward code- intensive behavior as shown in Figure 4. Specifically, as training progresses, the model increasingly favors code-related actions, ultimately resulting in a slight performance degradation relative to the initial SFT checkpoint. Within a mixed GUI/code training sample, a code action typically contains substantially more assistant tokens than a GUI click or keystroke. Standard GSPO averages token- level log-importance weights over all valid assistant tokens in the sample. Thus, even when a long code action constitutes only one of several GUI and code steps, it can dominate both the sample- level importance ratio and the clipping decision. This motivates an aggregation in which the weight assigned to each action step in the sample-level log-ratio is no longer determined by its token count. Step-balanced GSPO modifies only the aggregation of the sample-level ratio.
