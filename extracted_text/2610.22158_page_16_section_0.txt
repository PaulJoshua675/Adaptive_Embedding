For ev- ery mechanism, a judge returns one of supported, not_supported, or uncertain. supported re- quires the mechanism’s positive test and the re- quired evidence; not_supported means the avail- able record is sufficient to determine that the test is not met; and uncertain is reserved for cases in which missing context prevents a defensible de- cision. Evidence for M01, M02, and M04 must include an exact quote of the affected requirement from the current flawed question and an exact quote from the response’s reason or SQL show- ing the transformation. M03 instead requires an erroneous availability or answerability inference in the response plus counterevidence from veri- fied model-visible context. The output also records the target requirement, transformation type, con- text basis, a concise explanation, and three con- trol fields: whether the target is complete and ex- plicit, whether any partial implementation remains, and whether the response supplies a concrete re- placement. Deterministic post-processing validates the required quotes, context basis, control fields, and same-target exclusivity, and then derives the positive-label list only from validated supported verdicts. M01, M02, and M04 are mutually exclusive when they describe the same atomic requirement: a concrete substitute is M01, a changed satisfac- tion relation for an explicit contradiction is M02, and complete disappearance without replacement is M04. They may coexist only when they concern distinct requirements. M03 is independent, but the same inference from nonappearance in bounded examples is not counted again as M01. Complete abstention alone is not M04, and ordinary SQL im- plementation defects are outside this mechanism taxonomy. Binary coding and strict consensus. The same binary coding is used for automatic and human reli- ability analyses: supported is coded as 1, whereas both not_supported and uncertain are coded as 0. A mechanism enters the reported label set only when both attribution judges mark it as supported. This rule is applied separately to M01–M04, so the final label set is simply the intersection of the judges’ supported labels; their complete four-label combinations need not match. All three evaluation fields must be valid: Detection and Type Identification must be binary, and SQL Behavior must be in {0, 1, 2}. An output is a candidate fail- ure when Type Identification= 0 or SQL Behav- ior̸= 2. Candidate records are paired only when their sample identity and their database ID, ques- tion, reason, and SQL match exactly. The two eval- uators must then agree on all three fields. Records with non-string reasons, schema-placeholder out- puts, or no usable reason/SQL evidence are ex- cluded because they cannot support mechanism attribution.
