The interface exposes six action categories. terminal_send submits literal text and named keys to an interactive terminal; terminal_read captures its screen or a bounded portion of its history; and terminal_new opens another independent shell on the same task filesystem. get_file retrieves a regular file, while send_path transfers a file or directory from the agent’s workspace to the task sandbox. Finally, finish submits the current task state and ends solving. Responses contain terminal snapshots, metadata, transfer acknowledgments, or retrieved file contents, depending on the action. Appendix A.4.1 lists the returned files. Terminal input does not wait for command completion. Processes continue between actions, and an empty or unchanged screen does not imply that a command has finished. A read may include a short fixed wait before capturing output, but it does not wait for a process to terminate. The agent must decide when to inspect output, send further input, interrupt a process, or work elsewhere. Thus, command execution is nonblocking with respect to completion, while observations are still delivered only in response to requests. We do not expose a dedicated execute-and-wait action. This is an interface choice, not a restriction of Terminal-Bench: its evaluation infrastructure supports direct command execution by custom agents [29]. An exec action with a short waiting limit would also fit our contract, but would define another environment version. Whether it helps is outside this study. Here Terminal-Bench tests the unchanged agent in a setting markedly different from the games, rather than serving as an interface-optimization exercise. Termination. Calling finish or reaching the task’s external timeout ends the solving phase and prevents further actions. In both cases, the verifier is run and its reward determines the task score; successful verification can therefore receive reward 1 after an agent timeout. If the verifier itself times out, the score is zero.
