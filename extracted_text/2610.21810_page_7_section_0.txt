Workload details appear in Appendix G. 5.1 Selective Lookup Lookup layouts. CP stores each row as an inde- pendent record, allowing only the requested rows to be fetched and reconstructed. In contrast, QTIP’s tiled representation distributes each row across mul- tiple code fragments. To enable selective access with this layout, we implement a tile-window de- coder that retrieves only the bit windows needed for the requested rows rather than entire tiles. We compare this decoder against our fused row-wise decoder under identical lookup requests, a two-bit code rate, and per-row scale storage. The tiled base- line uses random payloads, while CP uses encoded model tables, so this experiment isolates access cost rather than reconstruction fidelity. Lookup latency. We replay lookup requests from 4,096-token sequences constructed from held-out FineWeb-Edu text using the DeepSeek tokenizer on a single H200 GPU. Each token requests 48 rows across two Engram layers. With tables stored in GPU high-bandwidth memory (HBM), CP com- pletes the requests in 0.190 ms, compared with 0.221 ms for the tile-window decoder. When ac- cessing pinned host DRAM over PCIe, the corre- sponding times are 6.54 ms and 10.78 ms. These results demonstrate that CP’s row-wise representa- tion supports efficient selective lookup, with partic- ularly large benefits when accessing tables across PCIe. We report the mean of five independent run medians, each measured over 100 timed calls after 20 warm-up calls. Additional comparisons and memory-access analyses are provided in Ap- pendix G.1. 5.2 Workload Capacity Experimental setup. To evaluate the serving benefits of reduced memory usage, we distribute the DeepSeek backbone and tables across four or eight H200 GPUs. Our representative workload pro- cesses eight sequences with 4,096-token prompts and generates 256 tokens per sequence. We ad- ditionally evaluate larger workloads, including a decode batch of 512 sequences and a prefill step of 65,536 tokens across 32 sequences. Table 5 sum- marizes the results. Four-GPU serving. With four GPUs, the origi- nal FP8 tables occupy 50.7 GB per GPU, compared with 12.7 GB for CP. For the representative work- load, CP reduces prefill latency from 64.66 s to 13.27 s and enables larger workloads that otherwise run out of memory. Compared with the four-bit NVFP4 baseline, CP also reduces the 64k-token prefill time from 59.81 s to 18.23 s, while decode times remain similar. These results show that CP alleviates GPU memory pressure and improves per- formance for memory-intensive serving workloads. Eight-GPU serving. With eight GPUs, the orig- inal FP8 tables fit comfortably for smaller work- loads, and step times differ by at most 2.4% when memory pressure is limited. However, CP frees an additional 19.0 GB per GPU, allowing substantially larger workloads.
