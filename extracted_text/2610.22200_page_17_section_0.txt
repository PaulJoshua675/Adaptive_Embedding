It then presents the Cross-Device SDK, the programming interface through which the model operates different devices (Section 4.2), and the harness we built for real devices, organized into five layers with clear responsibilities (Section 4.3). 4.1 The Gap Between Benchmarks and Real Machines Controlled computer-use evaluations typically provide prepared task states, an initial instruction, and an environment reserved for the agent. Such settings simplify evaluation but do not fully capture the demands of operating a user’s computer. We highlight five requirements that become especially important when the agent works alongside a user in an existing, changing environment. The user and agent share control. The user may continue working while the agent runs, so the agent cannot assume exclusive control of the pointer, keyboard, or focused window. It must account for user activity rather than attribute every change to its own actions. Where supported, it should prefer accessi- bility actions or background-window operations that leave the user’s current interaction undisturbed. When these methods cannot complete an operation, foreground interaction requires coordination with the user before taking control. The screen keeps changing. Application windows open, close, and move, and one window can cover another. These changes may come from applications unrelated to the task and continue while the agent is reasoning. A coordinate or element reference that was valid when observed may therefore be wrong by the time the agent acts. User requests evolve during execution. Users may clarify an initial request, correct the agent’s approach, or add constraints as work proceeds. The agent must keep track of the overall task goal and relevant progress across interruptions and turns, while revising its plan to reflect the user’s latest instructions. Observation and control require explicit targets. On a user’s computer, the task-relevant application, window, or browser tab need not be in the foreground.
