C Software Editing Experiments We describe the Java refactoring benchmark and evaluation, then analyze demonstration condi- tioning, length allocation, and example guidance. C.1 Benchmark Construction and Evaluation Setup We derive multi-site editing tasks from Extract Method commits in SWE-Refactor (Xu et al., 2026b), which provide before-and-after snapshots and extracted helpers. For each (repository, commit, file, helper) group, we identify updated callers and represent each minimal changed region as a <old>/<new> pair. A seeded file-order rule assigns D accepted edits as demonstrations and J remaining sites as targets. Eligibility rules fixed before inspecting outcomes exclude edits requiring identifiers or literals absent from the prompt or changing asserted values. We also limit replacements to 80 LLaDA tokens and enclosing methods to 200 lines, retain one helper per commit and file, and collapse mirrored commits. The resulting benchmark contains 127 tasks from 50 commits across 14 repositories, with (D, J) ∈{1, 2}2 and at most one task per group and configuration. Because eligible commits differ across configurations, comparisons across (D, J) in Table 1 do not isolate the effect of demonstration or target count; results are aggregated and bootstrapped by commit. For P0, only changed-line tokens of demonstration outputs are masked. Evaluation procedure. Frozen LLaDA-1.5 (Zhu et al., 2026) generates K = 16 rewrites per task under each length setting; unguided sampling and example guidance use the same stored samples. We use Claude Sonnet 5.5 (claude-sonnet-5-5) as a Claude Code sub-agent, with a fixed judging rubric and fresh context per call. Each judging packet contains the helper and its Javadoc, accepted demonstrations, and target methods with candidate rewrites inserted, but excludes developer references, generation settings, length allocations, and model scores. The judge assesses whether the edits adapt receivers, arguments, and control flow while plausibly preserving behavior; equivalent rewrites may pass, while incomplete or erroneous edits fail. Joint success requires every target to be judged correct; uncertain judgments count as failures, and ill-posed packets remain in the evaluation. Duplicate candidate texts are judged once per task, but duplicate draws remain in the sample pools; we report unadjusted 95% paired commit-bootstrap intervals. We do not compile or execute the generated code. Judge checks and limitations.
