Figure 3: Scripted controller used by both prompt variants. The initial prompt includes the selected continuation instruction. State is inspected after Codex returns; “No progress” means no new action since the preceding continuation. “End” denotes controller exit after environment termination or a return with no new action following the stuck reminder. The runtime-recovery supervisor is omitted; its handling of controller exits is described in the text. Normal protocol. The controller resumes the same Codex conversation with a reminder to keep working toward the goal in the environment description (Appendix B.1.2), followed by the variant-specific instruction. The first nonterminal return receives this continuation even if the initial invocation took no action. Stuck protocol. If a continuation produces no new environment action, the controller adds the no-action reminder (Appendix B.1.3). If Codex again returns without taking an action, the controller exits. If the environment remains nonterminal, this exit triggers recovery, subject to the recovery limit described below. This is a fallback for repeated non-action. Recovery. In our previous experiments, Codex occasionally exited with a runtime or service error, or appeared to freeze while its process remained alive but stopped producing observable activity [9, Section 4.7, “Runtime recovery”]. Following that work, we use a recovery supervisor to continue execution after such failures. The supervisor monitors the controller process and its activity log. When the process exits or the log remains inactive beyond the configured threshold, it restarts the controller if saved session state exists and the environment is still active.
