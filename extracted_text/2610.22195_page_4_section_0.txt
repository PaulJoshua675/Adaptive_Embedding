Method Given a task q and a set of worker roles and tools, HTN- Orchestrate separates global task planning from local sub- task execution through two cooperating layers (Figure 1). At the upper layer, the Planner incrementally constructs a hierarchical task network that encodes subtask decomposi- tions and their dependencies, while at the lower layer, each executable leaf subtask is delegated to an Orchestrator that schedules workers and returns a result. Because these re- sults flow back to the Planner, subsequent decomposition decisions reflect findings that were unavailable when the network was first constructed, and when the current de- composition cannot resolve the task, accumulated evidence supports the construction of a revised network. 3.1. Task Network Representation Following the HTN formulation (Erol et al., 1994), we rep- resent a task network as T = (V, Eh, Ed), whose root corresponds to q. The hierarchy edges Eh form a rooted tree in which each parent is decomposed into children that jointly address its task, and the dependency edges Ed im- pose acyclic precedence constraints among siblings, with an edge (u, v) indicating that v requires the result of u. We denote the children and direct prerequisites of v by Ch(v) and Pred(v), respectively. Unlike classical HTN planners that draw from a predefined library of decomposition rules, our Planner uses an LLM to generate decompositions during execution, which allows the network to grow incrementally as prerequisite results become available. Each node stores its task description, execution status, and result summary yv (Appendix B lists the full node fields and prompt templates). The resolved-or- open distinction instead feeds into synthesis and replanning decisions that determine whether further work is needed. 3.2. Result-Informed Planning The Planner uses prerequisite execution results to guide sub- sequent task decomposition and retains accumulated find- ings to support replanning, as summarized in Algorithm 1. For each ready leaf, PlanOrExecute considers the original goal, the task description, its ancestors, and summaries of relevant prerequisite results, and based on this context either marks the task for direct execution or expands the network with children and their sibling dependencies. Because a dependent subtask receives its decomposition only after its prerequisites return, its internal structure can reflect their findings rather than relying on assumptions made before execution began.
