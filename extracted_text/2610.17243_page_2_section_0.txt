Never-Ending Language Learning (NELL) emphasized persistent learning from Web content [Carlson et al., 2010]; DeepDive demon- strated large-scale knowledge-base construction using sta- tistical learning and inference [Niu et al., 2012]; and Knowledge Vault combined Web extraction with proba- bilistic knowledge fusion [Dong et al., 2014]. EneMonIE narrows this general objective to the energy domain, where entities, events, dates, technologies, organizations, and public opinions must be related across sources. Several components of the original design are well- established NLP tasks. NER over informal text is challeng- ing because social media frequently departs from conven- tional spelling and syntax [Ritter et al., 2011]. Temporal normalization links textual expressions to comparable dates [Strötgen and Gertz, 2010], while event extraction structures occurrences that may have policy, operational, environmental, or technological consequences [Ritter et al., 2012]. Sentiment analysis provides a coarse represen- tation of expressed opinion [Pang and Lee, 2008], and multi-document or social-media summarization reduces repeated evidence to concise statements [Chakrabarti and Punera, 2011]. Energy ontologies further provide domain vocabulary and conceptual structure [Küçük, 2015]. An executable architecture must coordinate these tasks and define their data contracts. In particular, down- stream clustering should not operate on raw text alone when normalized entities, event types, and dates are avail- able. Similarly, question answering should not bypass the semantic pipeline when live Web pages are collected. EneMonIE-Backend addresses these concerns by using one normalized document model and one processing function for both scheduled ingestion and question-driven evidence collection. 2.2 Design requirements The redesign follows six requirements: 1) Modularity. Source-specific acquisition and semantic analyzers must be replaceable behind stable interfaces. 2) Early filtering. Non-energy documents must be rejected before semantic extraction and persistence. 3) Traceability. Every de- rived object must remain connected to its source document and, where available, its original URL. 4) Determinism by default. Core extraction, storage, ranking, and fall- back answering must operate without a remote language model. 5) Evidence grounding. Generated answers must be based on a bounded evidence set rather than unconstrained model knowledge, following the grounding motivation of retrieval-augmented generation [Lewis et al., 2020]. 6) Application independence. Transport and presentation layers must not own the semantic pipeline or the database model. 3 Proposed Architecture Figure 1 presents the complete backend architecture. The main pipeline consists of five layers, while a separate lower section illustrates question-driven execution paths that reuse the same processing and persistence services. More specifically, the upper pipeline is responsible for acquiring, normalizing, analyzing, organizing, and stor- ing energy-related documents, whereas the lower sec- tion presents three backend question-answering workflows. User-interface, web-server, and visualization components are intentionally excluded from the architectural design. 3.1 Layer 1: heterogeneous data sources The first layer represents both configured and on-demand inputs. Configured sources include RSS news or video feeds, lists of Web pages, arXiv queries, social-media records stored as JSON Lines, and open energy data represented as CSV. These inputs cover the principal media types identified in the original EneMonIE proposal while making each acquisition mechanism explicit. Question-driven Web retrieval is modeled separately because its lifecycle differs from scheduled polling. In- stead of collecting all items from a predeclared source, it transforms a question into an energy-oriented query, obtains candidate results, downloads a bounded number of pages, and submits those pages to the standard seman- tic pipeline. This design prevents the question-answering path from becoming an unfiltered shortcut around En- eMonIE processing. 3.2 Layer 2: acquisition and normaliza- tion All configured connectors implement a common fetch operation and return a normalized Document. A document contains a stable identifier, source type, source name, title, text, URL, language, publication time, and arbitrary metadata. Source adapters hide format-specific details such as RSS XML, arXiv Atom records, HTML cleaning, JSONL decoding, and CSV row serialization. Normalization is followed by identifier-based dedupli- cation. Within a collection run, documents are indexed by doc_id; repeated identifiers overwrite earlier occur- rences before semantic processing. At storage time, the same identifier becomes the relational primary key and en- ables idempotent upserts.
