LCT: Losslessly Compressed Tensors A Experimental Details The main experiments are conducted on an NVIDIA RTX 3090 using PyTorch 2.14 (Paszke et al., 2019) with Triton 3.8 (Tillet et al., 2019). The evaluation across GPU models in Table 8 used the described GPUs, with an older PyTorch 2.11 setup for compatibility with the older GPUs. Training measurements. For the NanoGPT and Qwen timing and memory comparisons, we discard three warm-up optimizer steps and measure the following five steps. We report the mean step time and the largest peak memory across those five steps. Wall-clock timing is synchronized with CUDA before and after each step and includes batch preparation, forward and backward computation, and optimizer updates. Model loading and setup are outside the timed region; initial compilation, where enabled, is performed during warm-up. Validation and checkpoint saving are excluded from these measurements. Peak memory is measured with torch.cuda.max_memory_allocated(), resetting the peak counter before each step. This includes persistent tensors, temporary allocations, and the full shared overflow buffer when used. Values are reported in MiB and measure allocated tensor memory rather than the CUDA allocator’s reserved memory. A.1 Baseline codec evaluation We compare LCT, SplitZip, DFloat11, ZipNN, and nvCOMP with LZ4, Bitcomp, and ANS on the encoding and decoding task in Section 6.1. The input contains 229 BF16 elements (1 GiB), sampled on the GPU from N(0, 22) in FP32 and then converted to BF16, using random seed 0. Codec configuration. SplitZip, DFloat11, and ZipNN use the official implementations. SplitZip’s codebook is calibrated on a separate tensor of the same size and distribution. The calibration time is excluded from timing since it is intended to be done once before use. DFloat11 uses a native C encoder on the CPU and the upstream CUDA decoder. Its encoding time includes histogram and codebook construction, transfer of the input to the CPU, and transfer of the compressed buffers back to the GPU. ZipNN uses Huffman coding with eight CPU threads. The encoding time includes the input transfer to the CPU, and decoding includes transfer of the reconstructed tensor to the GPU. LCT uses the Gaussian model, with a shared overflow arena allocated before timing. The nvCOMP methods all use the default configuration. Timings include any setup and codec configuration done as part of the library. Timing and storage. Each codec performs three warm-up encode–decode cycles, followed by 50 measurements of each operation. Encoding and decoding are timed separately with a wall-clock timer and CUDA synchronization at their boundaries. Input generation, codec initialization, and output cleanup are outside the timed regions; allocations and transfers performed within each codec call are included. The reported means therefore measure complete codec calls, including host overhead. Timing uncertainties are standard errors of the mean, computed as the sample standard deviation divided by √ 50. Compression ratios divide the original tensor size by the compressed representation size. Baseline sizes include the encoded payload and decoding metadata; LCT uses the storage charged to the compressed tensor, including its overflow allocation, rather than the full capacity of the shared arena. Additional GPU evaluations. Table 8 reports the codec comparison using a 1 GiB Gaussian tensor on NVIDIA V100 and A40 and a 4 GiB Gaussian tensor on NVIDIA H100. LCT has the lowest encoding time among the reported methods on all three GPUs, while SplitZip has the lowest decoding time. LCT’s storage geometry was changed on the V100 and H100, using 32,768 elements per block rather than 65,536, with stream configurations changed accordingly to match the compression ratio. This allows for better parallelism on the more powerful GPUs. Our V100 setup does not support nvCOMP methods. Scaling with input size. Figure 3 compares encoding and decoding throughput for inputs from 16 to 2048 MiB. LCT’s encoding throughput exceeds SplitZip’s from 64 MiB onward, reaching approximately 396 GiB/s at 2048 MiB. Their decoding throughputs are similar for larger inputs, both reaching approximately 385 GiB/s at 2048 MiB. A.2 Fused pointwise operator evaluation Each pointwise operation was benchmarked. Each input contains 229 BF16 elements (1 GiB). Addition operands are sampled on the GPU from N(0, 22). For multiplication, the second operand instead follows N(1, 0.012) with seed 2, to keep the multiplier concentrated near one.
