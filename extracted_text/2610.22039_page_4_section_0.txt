WEAVE therefore represents PRs at the level of typed change loci and calibrates their shared evidence against repository-specific modification patterns. Typed change loci. For each PR p, we extract a set of typed change loci L(p) = Last(p) ∪Lsym(p) ∪Lcfg(p) ∪Ldecl(p) ∪Ldep(p). (2) These loci capture AST declarations, lightweight symbols, structured configuration or schema entries, and dependency keys. Thus, a PR is represented by the concrete program enti- ties and structured entries it changes, rather than by the files it touches. Type-specific extraction prevents configuration files, manifests, and lockfiles from being treated as single shared locations. Test files, generated or vendored code, and binary diffs are excluded from aggregation. Detailed extrac- tion rules are provided in Appendix. Repository-calibrated coupling. The evidential value of a locus depends on how frequently it is modified within its repository. Let PR be the candidate PR set in repository R, NR = |PR|, and dfR(ℓ) = |{p ∈PR : ℓ∈L(p)}| be the number of PRs touching locus ℓ. We assign ℓthe repository-local inverse- frequency weight wR(ℓ) = log  NR + 1 dfR(ℓ) + 1  + 1. (3) The coupling score between PRs pi and pj is then defined as sR(pi, pj) = P ℓ∈L(pi)∩L(pj) wR(ℓ) P ℓ∈L(pi)∪L(pj) wR(ℓ). (4) This weighted overlap suppresses repository-wide hubs and emphasizes specific, infrequently modified loci that provide stronger evidence of continuous engineering work. Edge filtering and bounded DAG assembly. Candidate relations are constructed only within the same repository: Ecand R = {(pi, pj) | ti < tj, tj −ti ≤∆, sR(pi, pj) ≥θ} , (5) where ∆is the search radius and θ the minimum coupling threshold. Merge time only constrains search and orients edges; temporal proximity does not indicate coupling. We remove relations induced by repeated or reversed changes, including reverts, backports, release replays, and near-duplicate patches. The remaining edges define repository-level connected components. Components of at most K nodes are retained; larger ones are reduced to high- scoring connected subgraphs. Preserving all surviving edges among selected nodes yields bounded dependency DAGs with linear, fork, join, and mixed structures. Merge-time lin- earization is used only as a baseline. Appendix details further filtering and graph assembly. 3.3 Executable Task Instantiation A dependency DAG defines the scope of a candidate task but does not by itself provide an executable benchmark instance. WEAVE therefore constructs a unified repository state, task specification, and test oracle for each retained graph. Figure 3: Composition and structural characteristics of WEAVE-Bench. (a) Language balance and PR scale. (b) Dependency-DAG complexity and patch scope. Executable task instantiation. For each candidate graph G, we start from a repository state Sgold containing all con- stituent PRs and revert their changes to construct the coun- terfactual base state Sbase, while preserving changes outside G. We then consolidate the PR objectives into a single task specification q, removing PR identifiers, commit metadata, and historical implementation details. The agent solves the task in a single repository state and returns one patch, without reproducing the original PR sequence. The combined executable oracle must satisfy TF2P(Sbase) = fail, TF2P(Sgold) = pass, (6) while preserving the required TP2P behavior. Candidates are discarded when repository reconstruction, gold-patch appli- cation, or executable validation fails. Node attribution and corpus construction. To support graph-conditioned credit, each valid F2P test is assigned to a PR node when high-confidence attribution is possible: A : TF2P →V ∪{ambiguous, unattributed}. (7) Attributed tests enable node-level scoring, while all valid tests determine full-task correctness. We retain only exe- cutable instances with adequate attribution coverage and no recoverable target commits or repository history. Appendix details reconstruction and attribution. Validated instances are partitioned into WEAVE-Train and the held-out WEAVE-Bench. We enforce temporal sep- aration and eliminate overlapping target PRs, duplicate or near-duplicate patches, and other direct solution leakage across splits.
