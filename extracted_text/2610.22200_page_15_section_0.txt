The comparison evaluates these mechanisms jointly. 3.3.4 Code-Execution Ablation Code execution improves task scores and reduces interaction steps. We compare four execution configurations for Qwen3.8-Max, DeepSeek-V4.1-Flash, and GLM-5.3-Flash: single-action GUI execution, batched GUI actions, batched GUI+CLI actions, and code execution over GUI and CLI operations. In the selected runs, code execution achieves higher task scores and fewer steps than each alternative across all three models (Figure 6). Relative to batched GUI actions, task scores improve by 15.5 to 33.6 points, while steps per task decrease by 55.3% to 63.1%. Executable control adds value beyond GUI+CLI access. The batched GUI+CLI baseline provides the same interfaces and already supports shell scripts. Nevertheless, code execution raises GLM-5.3-Flash’s task score from 55.8 to 63.2, a gain of 7.4 points, and reduces Qwen3.8-Max’s steps per task from 66.1 to 54.9, a 17.0% reduction. The key distinction is how operations are coordinated within a step. A batch fixes the sequence of GUI and shell actions in advance, whereas a program can use intermediate results to determine subsequent operations across both interfaces. Loops, conditional branches, and retries can thus consolidate work that might otherwise require multiple model calls. This unified interface also lets models apply their existing programming capabilities directly to computer interaction, rather than expressing computer interaction through a separate action-list format. Together, these properties may help explain the observed improvements in task scores and interaction efficiency. 3.3.5 Harness-to-Model Decision Transfer Ablation Most mechanisms are not designed primarily to improve task scores.
