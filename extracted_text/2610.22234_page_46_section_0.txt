G.6 INSTRUCTION QUALITY REVIEW PROMPT Instruction Quality Review Prompt (Simplified Version) # Role and Objective Critique every GUI task proposal and accept at most ‘target_count‘. Use ‘rationality_score‘ as the primary quality signal; require strong verification and answer-isolation scores. Treat ‘complexity_score‘ as descriptive only. # Review Dimensions - Grounding and feasibility: the task is reachable from ‘config‘, uses only initialized ‘related_apps‘ and ‘used_files‘, and makes no hidden assumptions. - Clarity and realism: ‘instruction‘ is a concise user goal rather than a tutorial; it identifies exact paths, objects, destinations, output shape, and constraints. - Verification sufficiency: ‘success_criteria‘ and ‘evaluation_requirements_text‘ are complete, mutually consistent, and precise enough to implement without access to exploration screenshots. - Answer isolation: ‘instruction‘ does not reveal values that must be obtained by reading, counting, comparing, transforming, or inspecting source material. - Rule grounding: require stable deterministic checks whenever VM files or command output capture the condition; file existence alone is insufficient. Visual-only conditions require an explicit, task-specific VLM rubric. - Safety and stability: reject destructive or irreversible state changes, package installation, external side effects such as messaging, subjective-only goals, and current web/date dependencies. - Data and config fit: sampled artifacts are used when relevant, target paths and application state match ‘config‘, and existing files are edited in place unless the goal explicitly requests a new output. - Diversity: avoid recent task patterns and filename-only variants recorded in application memory. - If multiple applications are genuinely required, ‘dependency_chain‘ must state a verifiable source-to-operation-to-target dependency; do not reward unrelated parallel actions merely for involving more applications. # Scoring and Selection Use integer scores from 1 (unusable) to 5 (excellent). - ‘rationality_score‘: realism, reachability, grounding, safety, and unambiguity. - ‘complexity_score‘: planning horizon, transformations, precision, and state. - ‘success_criteria_score‘: completeness and consistency of the verification contract. - ‘instruction_leakage_score‘: withholding derived answers while remaining clear. Reject low-quality proposals directly. For each rejection, provide a short machine-readable ‘reason‘ and actionable ‘suggested_repair‘. Rank accepted items by ‘rationality_score‘, using verification and leakage scores as quality gates. # Output Return valid JSON only: { "proposal_scores": [{ "proposal_id": "p01", "critic_scores": { "rationality_score": 1, "complexity_score": 1, "success_criteria_score": 1, "instruction_leakage_score": 1 }, "rationale": "brief score rationale" }], "accepted": ["p01"], "rejected": [{ "proposal_id": "p02", "reason": "short_reason", "suggested_repair": "concise actionable feedback" }], "coverage_summary": {} } 46
