No additional warning is provided re- garding potential flaws in the query. Implicit Setting The Implicit setting introduces implicit premise-awareness guidance. Models are informed that the input question may contain errors and are asked to assess its validity before answer- ing. The output JSON includes sql, is_valid, and reason, where is_valid indicates whether the model considers the question logically valid and answer- able. This setting measures whether soft prompting can improve premise validation and abstention be- havior. Explicit Setting The Explicit setting provides direct critique-oriented instructions. Models are explicitly told that the question contains logically flawed or incorrect premises, and are required to critically examine its assumptions before respond- ing. The output format remains sql, is_valid, and reason. This setting examines premise critique be- havior under an explicit assertion of a query flaw, which is supported for positive samples but false for negative samples. 3.5 Evaluation Framework For positive samples, three metrics are considered: SQL Behavior (SQL), Detection (DET), and Type Identification (TYPE). SQL Behavior measures the degree of abstention from generating mislead- ing SQL for a flawed query, using a three-level ordinal score from 0 to 2. Detection evaluates whether the model recognizes that the query con- tains a premise flaw, and Type Identification mea- sures whether it correctly identifies the correspond- ing failure type. For negative samples, two complementary met- rics, namely SQL Generation (GEN) and Valid- ity Judgment (VAL), are introduced. SQL Gen- eration measures the proportion of negative sam- ples for which the model generates SQL, reflecting whether it maintains generation for valid queries. GEN measures generation coverage; Appendix B.7 provides an execution-based validation showing that GEN closely tracks end-to-end execution suc- cess. Validity Judgment measures the proportion of negative samples explicitly judged valid through is_valid=true, indicating whether the model cor- rectly recognizes query validity. 4 Experiments 4.1 Experimental Setup We evaluate premise critique ability on a diverse set of state-of-the-art LLMs. The evaluated mod- els include ChatGLM-5.1 (GLM-5 Team, 2026), Claude Opus 4.6 (Anthropic, 2026b), Claude Son- net 4.6 (Anthropic, 2026a), Claude Opus 5.5 (An- thropic, 2026c), DeepSeek V3.2 (DeepSeek AI, 2025), DeepSeek V4.1 Flash (DeepSeek-AI, 2026), Doubao Seed 2.0 Pro (ByteDance, 2026), Gem- ini 3.1 Pro Preview (Google, 2026), LLaMA 4 Maverick (Meta AI, 2026), GPT-5.4 (OpenAI, 2026b), GPT-5.6-Luna (OpenAI, 2026a), GPT- 6-Luna (OpenAI, 2026c), GPT-6.1-Sol (OpenAI, 2026d), and the 35B, 122B, and 397B variants of Qwen3.5 (Qwen Team, 2026). Each of the 1,800 taxonomy-guided premise perturbations is paired with its unmodified source query. We treat the perturbed query as a positive sample, for which a model should detect the flaw and abstain, and the original query as a negative sample, for which it should recognize the query as valid and generate SQL. Each model therefore pro- cesses 3,600 requests under each of three prompt- ing settings, or 10,800 requests in total. Across 16 models, our evaluation comprises 172,800 model responses. We use temperature 0 and the default API configuration for each model. 4.2 Main Results Table 3 presents model performance on flawed queries and their paired originals. Across all three prompting settings, models exhibit limitations in premise critique ability, although these limitations take different forms. Base prompting reveals weak spontaneous critique, Implicit prompting produces partial and uneven improvements, and Explicit prompting exposes models’ susceptibility to the prompt’s assertion of a flaw. Together, these results show that current models do not reliably assess query premises across prompting settings.
