A Multi-Agent LLM System for Automated Tuning Standard and detailed Analyst prompts. The framework supports two modes of hypothesis generation. The standard prompt contains the Analyst role, problem statement, target metric, implementation constraints, required format of the technical specification, and complete experiment log. The detailed prompt retains these elements and adds a structured Chain-of-Thought procedure and a list of method classes specified by the Human Researcher for systematic exploration. Each hypothesis is assigned to one principal class, which is also stored in its experiment-log record, and the log is converted into a dynamically updated coverage map. For every class, the map reports the number of evaluated hypotheses, the best metric value, and a coverage status such as “not explored,” “limited data,” or “explored.” The map is included in the next Analyst prompt, which prioritizes suitable classes with little or no coverage and revisits an explored class only when a substantially different hypothesis is proposed. This mechanism structures an open natural-language search without reducing it to a finite list of implementations. The task-specific prompt configurations are described in Section 4; the detailed-mode prompt materials are provided in Supplementary Materials. 3.1. Run protocol One framework run is a series with a task-specific number of successful iterations. At each iteration, one hypothesis is tested in six steps: 1. The Analyst receives the task prompt and the current experiment log. At the first iteration, the log contains only the baseline record. In detailed mode, the current coverage map is generated from the log and included in the prompt. 2. The Analyst creates a technical specification according to the prompt template. In detailed mode, the specification also identifies the method class. 3. The Coder implements the specification subject to the corresponding software contract. 4. The code undergoes an automatic functional test on a small sample in the sandboxed environment. If the test fails, the error message, generated code, and original specification are returned to the Coder. The Coder analyzes the reported error and rewrites the code while preserving the proposed method and software contract; the revised version is then tested again. If valid code cannot be obtained within 10 attempts, the experiment is assigned the With error status; it does not count toward the run budget, and the framework proceeds to a new hypothesis. 5. Code that passes the functional test is evaluated according to the task-specific evaluation protocol, and the resulting metric is assigned the OK status. The budgets, metrics, data-use rules, and repetition schemes used in this study are specified in Section 4.5 and the accompanying appendices. 6. The Recorder combines the specification, validated code, execution result, and fitted hyperparameters into a JSON record and appends it to the log. The updated log becomes the external memory for the next iteration. 4. Experimental setup The same framework is applied to five tasks with different types of information representation: two spiking- network classification tasks, two boundary-value problems for the generalized nonlinear Schrödinger equation, and one boundary-value problem for the generalized Kuramoto–Sivashinsky equation. 4.1. SNN task: Correlation Classwise Network decoder The classifier is based on a Correlation Classwise Network (CCN) spiking neural network Sboev, Kunitsyn, Davydov, Vlasov, Serenko, Rybka and Liu (2025); Kunitsyn, Sboev, Davydov et al. (2025), whose weights are trained using a local spike-timing-dependent plasticity (STDP) rule. Image pixels are normalized and encoded as correlated spike trains that serve as the network input. The output spike activity of the leaky integrate-and-fire (LIF) neurons is then translated into a class label by the decoding module.
