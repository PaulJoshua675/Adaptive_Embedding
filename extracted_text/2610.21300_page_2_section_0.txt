Software used in a quality management system must be vali- dated for its intended use, including when it changes (ISO 13485:2016, subclause 4.1.6, incorporated by 21 CFR 820.10(a); 11–14), and electronic-record systems for “accuracy, reliability, consistent intended perfor- mance, and the ability to discern invalid or altered records” [15, §11.10(a)]; with a system whose output varies from run to run, a single difference observed after a change—to a document, an item, a model or the hardware—cannot be told from ordinary variation without repeated runs, and the individual assess- ments the change affects cannot be identified. An LLM pipeline does not give the same output for the same input by construction: floating-point reductions depend on how requests are batched [16], embeddings and retrieval drift with precision and with insertions [17], a commercial deployment runs on hardware and software the user cannot see [18], and in a recent preprint covering five API providers, repeated out- puts at temperature zero were character-identical 22% of the time on average for the two models evalu- ated on every task [19]. Reproducibility is a separate axis from accuracy, and this paper concerns only reproducibility. Deterministic inference is now available: batch- invariant kernels and, more recently, verified and scheduling-based engines make a model’s output inde- pendent of how requests are batched [16, 20–23]. What has not been tested is whether a complete assessment pipeline, in which inference is one stage among several, can be made reproducible, and what a user of a commercial deployment actually observes in the fields of an assessment record. We asked whether preliminary assessments of public FDA documents can be produced again, byte for byte, and found three things. Commercial LLM deployments did not repro- duce their assessments at the deterministic sampling settings they accepted: the quoted evidence changed more often than the label, one model varied differ- ently through different routes, another changed labels only between days, and reducing reasoning did not help. For the open-weight models we served, repro- ducibility was a property of how the model was served. A pipeline deterministic from text extrac- tion to inference reproduced every intermediate result and output across repetition, reordering, concurrency, interruption, corpus edits, machines and days for two device types, provided the GPU model and the inference engine’s configuration are held fixed and recorded; left to their defaults, OCR, embedding and approximate retrieval were themselves sources of vari- ation. We argue that, where judgments recorded in a quality system rest on LLM-prepared preliminary assessments, byte-level reproducibility of the entire pipeline is a strong and testable engineering con- dition for auditing those judgments and controlling change. It is not a regulatory requirement, and it is not sufficient for validation. Results Each preliminary assessment has four outputs (Table 1): a label (here Satisfied, Not satisfied or Can- not determine), a comment giving the reason, the passages quoted as evidence, and the files they come from. We compared repeated runs of the same prompt on six fields in two layers. The substance layer is what an expert relies on: the label, the cited files and the cited passages, where two runs cite the same passage when their quotations overlap at the same place in the same document. The text layer is what the assess- ment record stores: the exact quotation strings, the comment and the full output, compared character for character. Table 1 compares two of the five same-day runs of one prompt field by field; it illustrates how runs are compared, not which label is correct, since the study measures reproducibility, not accuracy. Commercial LLM deployments did not reproduce their assessments No commercial deployment returned the same output for every prompt, and twelve of fourteen changed at least one label (Table 2; Supplementary Table S13). A deployment is a model reached through a particular route: two OpenAI models through the OpenAI API and Azure OpenAI, three Claude models through the Claude API and Amazon Bedrock, and two Gemini models through the Gemini API and Google’s Agent Platform (Experiment 1; Figure 1). Each received 70 prompts built from public FDA documents for blood glucose meters, in three tiers of length (12 to 500 thousand characters), five times on each of two consecutive days, as byte-identical requests ask- ing for temperature 0, seed 0 and schema-constrained output wherever accepted and reasoning left at the provider’s default (Methods; Supplementary Table S1 gives every metric by tier). Within a single day, ten of the fourteen deploy- ments changed the label of at least one prompt. The number of such prompts ranged from 0 to 18 of 70 by deployment, the largest being gpt-6-luna through Azure OpenAI (Table 2). Two further deployments changed labels only between the two days, bring- ing the total to twelve (Supplementary Table S13). The sampling setting does not account for this.
