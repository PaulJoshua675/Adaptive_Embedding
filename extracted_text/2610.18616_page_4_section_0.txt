Output handling therefore affects both the current observation and the evidence available for later ac- tions (Sen et al., 2026). Following the use of output files in Pi (Zechner and Pi Contributors, 2026) and DR-DCI (Lu et al., 2026), our Pi implementation saves the complete output yt = run(at) of every shell command as a file ℓt in the task’s scratch directory. It presents the model with view(yt) = ( yt, |yt| ≤B, head(yt)∥nt∥tail(yt), |yt| > B, where B is the display threshold, head(·) and tail(·) return the beginning and end of yt, and the notice nt gives its full size and the path ℓt. This head-and-tail truncation bounds what enters the model’s context while retaining the complete ex- ecution result. Later code can search or filter ℓt, recover IDs omitted from the displayed excerpt, or combine its contents with other evidence. Ac- cess code can also return compact candidate lists or selected text fields, giving the agent control over the evidence presented in subsequent observations. Thus an output of tool use can become an input to subsequent tool creation. Appendix C specifies the thresholds and notice, while §2.6 describes the differences between harnesses. 2.5 Co-Evolving Toolbox Execution provides candidate IDs, intermediate sets, empty matches, and error messages. The agent can use these observations in later turns to choose another traversal, narrow a filter, inspect a file’s structure, or revise earlier code. The revised code determines which nodes and relations subsequent executions examine. Tool creation and tool use therefore co-evolve: evidence guides the construc- tion of access procedures, and those procedures guide further evidence gathering. In our Pi implementation, the toolbox Tt consists of access code retained in the interaction history for reuse and revision, while Lt denotes the saved shell-output files. When an action executes code pt and saves an output ℓt, these sets become Tt+1 = Tt ∪{pt}, Lt+1 = Lt ∪{ℓt}. For actions that contribute no access code or no saved output, the corresponding set is unchanged. Subsequent code can reuse snippets from Tt, read files in Lt, and incorporate IDs from earlier ob- servations. It can revise a failed computation or extend an earlier traversal with new constraints. The agent can also return to shell search or file in- spection whenever it needs more evidence. This process develops the access code within a task, without model training or a tool library learned across tasks. Section 3.4 examines these behaviors, with the measurement rules in Appendix G. 2.6 Implementation We instantiate DKGI in two general-purpose har- nesses: the minimal Pi (Zechner and Pi Con- tributors, 2026) and the more feature-rich Codex CLI (OpenAI, 2026a). Pi provides a simple setting for controlled ablations of graph access and agent- written code, with the model, harness, and budgets held fixed (§3.3). Codex tests the same design with richer runtime support. Both provide read- only graph files, a format description, a schema, and a writable scratch directory. Following Li et al. (2026), the Pi implementation supplements its bash and read tools with lightweight context manage- ment that retains code while replacing older tool results with placeholders as the context fills. We add the graph export, task prompt, output handling of §2.4, and an execution sandbox. In Codex, the model invokes shell commands, including Python, through JavaScript, with Codex’s own output and context management.
