AMD MI350X vs NVIDIA B200 Table I compares the GPU specs. AMD MI350X is built on the CDNA™4 architecture and is the first AMD GPU used for production-scale training at Meta. MI350X features eight accelerator complex dies (XCDs) with 32 compute units (CUs) each (a total of 256 CUs), a 288 GB HBM3e memory pool with up to 8 TB/s bandwidth, and 538 GB/s of scale-up bandwidth per GPU. B200 offers 180 GB of HBM capacity, with 900 GB/s of scale-up bandwidth per GPU. B200 and MI350X are same-generation flagships with closely matching theoretical bounds: their near-identical peak compute (2250 vs. 2300 BF16 TFLOPS) and HBM bandwidth (8 TB/s) yield largely coincident roofline curves [27], and thus a similar performance envelope for ML workloads. Their strengths are complementary: B200 leads on per-GPU scale-up bandwidth (900 vs. 538 GB/s), an all-to-all NVSwitch fabric (versus AMD’s point-to-point xGMI mesh), shared memory per SM (256 vs. 160 KB), and native TF32 support, whereas MI350X’s principal advantages are its 1.6× HBM capacity (288 vs. 180 GB) and higher deployed power. Hipification. Hipification is AMD’s CUDA-to-HIP (Heterogeneous-compute Interface for Portability) translation process that converts NVIDIA CUDA code into HIP equivalents; see Fig. 2. There are two primary approaches: (1) compile-time hipification using AMD’s open-source hipify-clang compiler, which translates CUDA constructs to HIP at build time, and (2) rule-based source-code translation using hipify_torch, which traverses and rewrites source files before compilation. While hipification provides broad functional compatibility and enables most CUDA workloads to run on AMD with minimal manual effort, performance portability remains a challenge. For instance, CUDA uses a warp size of 32, whereas an AMD GPU uses a wavefront size of 64. Kernels that naively hardcode warp sizes will likely perform suboptimally without tuning. The emergence of agentic AI tools has fundamentally lowered the cost of switching from NVIDIA to AMD. At Meta, we leverage AI agents to address issues in the hipification process. These agents iteratively compile code, interpret error messages, and apply fixes until the build succeeds. When a niche CUDA library lacks a ROCm equivalent, AI agents can even generate custom shims to mimic the missing functionality. This makes AMD GPUs accessible to a broad range of ML researchers, who can now deploy high-performance code without mastering low-level hardware nuances. Meta’s Usage of AMD GPUs. Meta started using the AMD MI300X [28] for inference in 2024. Today, models compatible with AMD GPUs make up over 60% of production model types, weighted by resource footprint. Training DLRMs, on the other hand, presents a greater challenge than inference: • Synchronization and network pressure: Training involves numerous GPUs in tight lockstep with frequent synchroniza- tion, heavily straining network efficiency. • Kernel and optimizer: Training requires comprehensive backward kernels and advanced optimizer support. • Generalization: While inference can be optimized per workload, training must rely on generalized optimizations for out-of-the-box performance—orders of magnitude more training trials run before a model is finalized, making per-job optimization infeasible. Addressing these challenges requires systematic optimizations across the software stack, from low-level libraries (Section III) and kernel tuning (Section IV) to high-level model co-design (Section V). III. ROOFLINE-DRIVEN OPTIMIZATION OF ROCM LIBRARIES The ROCm software platform provides optimized libraries, runtimes, and firmware for AMD GPUs. Grounded in roofline models [27] and hardware constraints, we optimize core GEMM kernels and selection algorithms to approach theoretical limits. To optimize RCCL, the collective communication library for distributed training, we derive theoretical bounds from hardware specifications as optimization targets. These roofline-driven prin- ciples enable low-level libraries to deliver robust, generalizable performance across diverse AI workloads. A.
