Reproduction can there- fore follow the recorded procedure without guaranteeing identical search trajectories. 3.2 Environments and policy interface Generated solutions must implement Solution(Policy), a Python class with an asynchronous action method. Policy objects receive the current observation, observation and action spaces, and task instructions. The policy interacts with the environment through an observe–act loop. Its runtime interface does not expose reward values or environment internals. A policy may retain state within an episode, provided it satisfies the required interface. That state must be reset at the start of each episode. Generation and repair prompts include task docu- mentation, resolved environment settings, the observa- tion/action contract, the objective, and execution con- straints. This documented task knowledge is distinct from the information exposed to a policy during execution. For BipedalWalker-v3, the prompts also include ex- plicit observation indexing, normalization, motor order- ing, and reward details. Prompt construction is config- urable by task. The study therefore evaluates program search with documented task knowledge, rather than learning solely from interaction. 3.3 Model configuration I used the requested model route openai/gpt-oss-120b: nitro through OpenRouter for proposal generation and repair. Responses were capped at 16,384 tokens per request. The runner does not explicitly set temperature or top- p, so the study does not specify fixed values for those parameters. Returned model, provider, and usage meta- data are retained when available. The requested route does not guarantee identical provider execution across requests.
