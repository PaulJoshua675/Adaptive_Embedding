BitSparse: Compact Activation Storage sequences with short references. Zstd similarly exploits repeated patterns, while also using entropy coding to improve compression ratio. Bitcomp is a proprietary format designed for numerical data and can efficiently encode sparse values. Cascaded combines techniques such as run-length encoding, delta encoding, and bit-packing. While these are general lossless compression codecs, they benefit greatly from activation sparsity, since the many zeros are easy to compress. Compressed Sparse Row. A standard format for sparse matrices is the CSR format. This stores the nonzero values, their column indices and a cumulative counter of row indices, and is well optimized for GPU multiplication, with native support on our GPUs. This method is however suboptimal for this setting, where sparsity is around 0.5 to 0.85, where the overhead from indices is significant. Currently, there is no FP8 support for CSR tensors. CompAct. Lossy compression has been considered. We compare against a recent method CompAct Shamshoum et al. (2025), which uses random Gaussian matrices to compress the hidden pre-nonlinearity activations into a lower dimension space. This method exploits the low-rank nature of activations. Training using CompAct demonstrates lower memory, with a small increase in training loss due to its lossy nature. The amount of compression can be tuned. We use CompAct-f to denote a compression factor of f, meaning its compression dimension is 1/f times the activation. A higher f gives lower memory and faster compression, at the cost of lower accuracy. D.3 MLP training benchmark setup Architecture and workload. The comparisons in Section 6.3 use a stack of eight residual MLP blocks. Each block applies RMS normalization, a bias-free linear expansion from 4096 to 21,504 features (the same as Nemotron-H), a ReLU or ReLU2 activation, and a bias-free projection back to 4096 features before adding the residual connection. Inputs are synthetic standard-normal batches with 16,000 rows and 4096 features. Parameters and activations use BF16. In this test, parameters are not updated since we are interested in the performance and memory for computing the gradients, not the optimizer. Each lossless method is validated by checking that its gradients match the dense baseline up to floating-point rounding. FP8 activation storage and matrix multiplication For the FP8 experiment we use FP8 only for the matrix multipli- cations and for the activation cache; the model’s parameters, inputs, and gradients remain in BF16. In each product the BF16 operand is cast to FP8 on the fly, so both the activation and the weight are represented in FP8-E4M3 for the GEMM, which accumulates in FP32 and returns a BF16 result. The activation cache stores the FP8 values themselves, together with the scale needed to interpret them. We use a separate tensor-wise scale for each operand, the weight and the activation. For the ReLU2 path, conversion is applied to the saved ReLU(Z) values. The implementation currently converts tensors to E4M3 FP8. The activation scale is stored alongside the sparse cache so that the values can be interpreted and scaled back during reconstruction. The weight scale is transient, recomputed each time the weight is cast, so keeping weights in BF16 and casting them per product adds no persistent parameter storage. Dense FP8 products use PyTorch’s scaled matrix multiplication primitive with tensor-wise scales. This scaling ensures the full dynamic range of FP8 values is used. Our method is also compatible with more advanced formats such as MXFP8 which use blockwise multiplication Open Compute Project (2023). Setup details. All methods use the same weights and inputs, fixed using a random seed. In order to generate sparse activations, the weights of the networks are shifted until the activations have the desired sparsity level. Every method uses a custom backward implementation which fuses the RMS norm layer via torch.autograd.Function. This is to ensure maximum efficiency since we found the default PyTorch implementation to be inefficient in its activation caching. In particular, fusing the RMS norm layer reduced the memory consumption of every method. Timing and memory. Each configuration is measured five times. Each measurement excludes one warmup for- ward/backward pass and is followed by three timed steps that are averaged for the displayed time. GPU execution is synchronized at the timing boundaries.
