3.2 DATA INFRASTRUCTURE The scale of computer-using agent training is ultimately bounded by the diversity of executable states from which meaningful tasks can arise. This is particularly important on desktops, where workflows are shaped jointly by applications, user artifacts, and persistent local state. We view authentic artifacts as a natural axis for expanding this state space, with artifact types and file formats providing a direct link to the applications that can operate on them. Based on this principle, we construct diverse executable desktop environments and synthesize grounded, verifiable tasks from the resulting states. 3.2.1 APPLICATION–ARTIFACT COMPOSITION FOR DESKTOP ENVIRONMENTS Real-world desktop workflows are commonly grounded in existing artifacts that are read, edited, or transformed through applications. Thus, we factor scalable desktop-environment construction into two reusable components: applications with fixed versions, launch procedures, and diverse initializa- tion configurations, and artifacts carrying authentic content and persistent state. Their compatibility- aware composition produces executable desktop states from which realistic tasks can arise. To instantiate such states at scale, we organize artifacts and applications into an application–artifact compatibility graph, whose edges are determined by the artifact types and file formats that applica- tions can consume. The underlying application configuration records these supported input types, together with the version, launch commands, and initialization settings required for reproducible execution. For example, a .pptx artifact can be connected to LibreOffice Impress and WPS Pre- sentation directly, whose application configurations specify how each application is launched with the file and which application-specific initialization settings are required. The resulting states are instantiated on reproducible Ubuntu virtual machines for task synthesis and trajectory collection. 3.2.2 ENVIRONMENT-GROUNDED TASK SYNTHESIS Given the diverse desktop environments constructed above, we next translate environment diversity into training-task diversity. Each synthesis episode first samples a target application and then selects compatible artifacts via the application–artifact compatibility graph, thereby instantiating a coherent and executable task context. Relying primarily on model priors tends to produce generic, repetitive instruction patterns and un- derutilize the state diversity of instantiated environments at scale. We therefore ground instruction generation in active exploration of the current environment. To avoid repeatedly covering familiar functionality, we maintain a global application memory that records functions previously exercised for each application and exposes this history during subsequent exploration, encouraging broader coverage over time. The Exploration Agent receives this memory together with application meta- data, exact file paths, launch configuration, tutorial, and initial screenshot, and performs a short non-destructive exploration restricted to opening, clicking, scrolling, and terminating. Based on the observed artifact content and application state, it proposes a realistic user instruction together with its initialization configuration and observable success conditions, without prescribing a GUI/code solution or revealing answer-critical information. To make synthesized tasks consistently verifiable, we adopt an everything-is-a-file abstraction in which terminal conditions are mapped, whenever possible, to inspectable file representations, and evaluator synthesis selects rule-based, VLM-based, or hybrid checks according to their observability. Verification specifies the desired terminal state without constraining how it is reached, allowing the same task to be completed through GUI interaction, code execution, or their combination. We decouple the instruction proposal from evaluator synthesis. Once an instruction proposal is ac- cepted, its instruction and success conditions are frozen and passed to an independent Evaluator Agent, which compiles the corresponding verification logic. Programmatically observable condi- tions are evaluated primarily with rule-based checks over VM files and command-line state, while visual conditions that cannot be reliably recovered programmatically are handled with VLM-based evaluation. Instructions and evaluators are validated separately in the pipeline. Instructions are checked for reachability, unambiguity, realism, and sufficient verification conditions, while evalua- tors must compile and assign zero reward to the initial state.
