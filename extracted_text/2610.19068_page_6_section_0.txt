As a result, architecture choice at retrieval time fully determines downstream behavior: PtR’s planner generates more ambitious plans on G3 (4.1 intended steps, 1.4 APIs named vs. 3.6 steps, 1.1 APIs) and uses a higher fraction of retrieved APIs (27–29% vs. 21–27%), reflecting the broader, more coherent candidate sets produced by stub-guided retrieval. PtR’s discovery call adds ∼75–104% token overhead (Appendix E, Table 8); on G1 this hurts (−0.072 recall) while on G2 it pays off (+0.042 recall). Beyond token cost, this discovery call sits on the critical path: because discovery and retrieval are sequential, PtR adds one full LLM round-trip of latency before retrieval and planning begin, so the overhead is both a token cost and a wall-clock latency penalty. Complexity- adaptive routing (using RtP for G1, PtR for G2/G3) saves ∼16% of total inference tokens, or ∼36% of the PtR discovery-call overhead, with no retrieval quality loss relative to always selecting the better architecture per subset, and eliminates the extra round-trip entirely for G1-type queries. The crossover maps naturally onto single-tool vs. multi-tool intent; practical proxies computable before any LLM call include query length, clause count, named-entity density, and the presence of conjunctive sub-goals — all of which correlate with the G1/G2 split in ToolBench. Most directly, RtP’s own top-1 cosine similarity is a zero-cost routing signal already produced by the pipeline: a high top-1 score indicates the query names an API directly (high Intent-Registry Coupling, G1-like) and can stay with RtP, whereas a low or diffuse score indicates abstract multi-step intent (G2/G3-like) that benefits from PtR’s stub decomposition — so a simple threshold on this score routes queries with no extra model and no extra call.
