Some label changes appeared only between days. For thirteen of the fourteen deployments, label differ- ences between the two days were no larger than within a day (Supplementary Table S13). The exception was gemini-3.8-flash: through both Google routes it gave the same label in all five runs of each day on every prompt, yet on one and two prompts the label of the second day differed from that of the first, under an unchanged model identifier, and the probability that two of its outputs differed rose from 0.01–0.09 within a day to 0.18–0.52 across days. A one-day val- idation of its labels would have called them stable. Prompt caching did not explain the variation either: through the OpenAI routes the probability that two runs differed was the same whether neither, one or both calls reported a cached prefix, and only through the Gemini API was it associated with cache state (Supplementary Table S5). Reproducibility depended on how the model was served The same open-weight model was reproducible or not depending only on how it was served. As a posi- tive control, we sent the 70 prompts, on the same schedule, to the judgment stage of the determinis- tic pipeline described below (“Ours” in Table 2): Gemma 4 31B (FP8) served by vLLM with batch- invariant inference [16, 20] on one NVIDIA RTX PRO 6000 GPU; all 700 outputs over two days were byte- identical, including prompts of about 130,000 tokens. A dedicated server sent one request at a time might be stable without any special measure, so we also sent the prompts from eight concurrent senders with batch invariance enabled and disabled, all else equal. Enabled, all 350 outputs were byte-identical to the sequential outputs; disabled, the full output varied on 58 of 70 prompts and the label on 5, and Qwen3-32B showed the same pattern, while Qwen3.8-27B could not be served in batch-invariant mode at all (Supple- mentary Table S7). Batch invariance lengthened the concurrent run by 18%. This changes one thing on one server, and is a direct form of the attribution that Rover et al. reached indirectly: variation comes from how the serving infrastructure executes a request, not from cloud hosting as such [19]. A complete assessment pipeline can be reproduced end to end Every intermediate result and output of a complete assessment pipeline was byte-identical across every operation we tried, for two medical device types, on one GPU model and one engine configuration (Table 3); we write Θ for the configuration, every- thing other than the inputs that can change an output (Methods). The pipeline (Figure 3) extracts text from each document, reading scanned pages by OCR, splits it into chunks, embeds each chunk, and stores chunks and vectors under hashes of their content; for each device–item pair it retrieves the six chunks that best match the item among that device’s doc- uments, scoring every chunk in scope exactly, builds the prompt, and has the judgment model (Gemma 4 31B, as above) write the preliminary assessment, whose quotations are then checked against the source by rule. One run does this for every pair from an empty database and records a hash at every stage (Experiment 2). We ran the pipeline on the 337 public FDA PDFs for blood glucose meters (3,150 pages, 100 of them read by OCR) and judged 776 device–item pairs over 83 devices. A reference run did this once, and we then repeated the whole process under operations that should not change the result—from fresh databases; interrupted and resumed during ingestion, including during OCR, and during judgment, with and with- out a restart of the inference server; with documents in reverse and in hash order; with 4 or 16 documents ingested and 1, 8 or 16 items judged concurrently; with a document added, assessed and deleted; on another machine with the same GPU model; and on a later day. Every per-stage hash matched the reference run for all 337 documents and all 776 assess- ments, and deleting the added document restored the database snapshot byte for byte. Determinism is not insensitivity to input: 19 of the 20 questions assessed for more than one device received different labels for different devices, and 746 of 776 comments are distinct. On infusion pumps—85 PDFs and 12 assessment items chosen by a rule fixed before the documents were fetched, 516 pairs—four runs in dif- ferent orders, concurrencies and days agreed on every per-stage hash. Each GPU stage needs its own invariance. Removing batch invariance from one stage at a time, on the reference GPU, moved that stage’s output and no other (Table 3).
