To enable adaptive reasoning, AURA learns a utility estimator that predicts the retrieval specificity of the current intermediate state. For each state zt, we define its target utility as yt = S(zt), (7) which represents the observed state-level retrieval utility. The estimator Vϕ(zt) (8) is trained to preserve the ordering of state utility using a pairwise ranking loss: Lrank = −log σ(Vϕ(zi) −Vϕ(zj)) , yi > yj. (9) Since adaptive stopping and state selection depend only on the relative ordering of reasoning states within a query trajectory, this objective targets or- dinal agreement rather than absolute score calibra- tion and is less sensitive to query- and negative-set- specific shifts in the scale of retrieval specificity. At inference time, reasoning terminates when the predicted state utility has not improved for p con- secutive steps, and the generated state with the highest predicted utility is used for retrieval. The utility estimator is a lightweight MLP over prefix- conditioned embeddings. 4 Experiments 4.1 Training Data Construction We build on the publicly released training data with 101K query-positive-negative samples from ReasonIR (Shao et al., 2025), which provides reasoning-intensive queries with paired positive documents and hard negatives synthesized from MS MARCO2 seed documents. To obtain rea- soning trajectories for utility supervision, we sam- ple G=8 independent trajectories per query from DeepSeek-R1 (Guo et al., 2025), each truncated to 2https://huggingface.co/datasets/microsoft/ms_ marco a maximum of l=2,048 tokens. Each trajectory is segmented at sentence boundaries into intermedi- ate reasoning states. After the retrieval warm-up described below, we compute retrieval specificity S(zt) for every intermediate state using the labeled positive document and hard negatives provided by ReasonIR. Trajectories where no intermediate state improves over the initial query embedding are removed during label construction, retaining 67.5% of sampled trajectories (approximately 5.4 per query on average), for approximately 545K reasoning samples. 4.2 Training Procedure Training separates label construction from utility- aware optimization. First, we warm up the unified model for one epoch with the multi-task objective but without utility-guided weighting. We freeze this warmed-up checkpoint to construct retrieval- specificity and state-utility labels. The utility es- timator Vϕ, a 3-layer 10M-parameter MLP with ReLU activations, is trained on these frozen em- beddings with a per-GPU batch size of 256 and a learning rate of 5 × 10−4 for up to ten epochs, with early stopping based on loss convergence. We then enable utility-aware weighting and continue joint optimization of the unified model. AdamW is used throughout. This schedule avoids constructing labels from the backbone’s initial, non-retrieval- adapted representations. 4.3 Implementation Details Experiments are conducted on 8 NVIDIA H100 GPUs, consuming approximately 100 GPU hours to converge. We adopt Qwen3-4B-Instruct as the backbone model and use a per-GPU batch size of 128 and a learning rate of 1×10−5. The embedding dimension matches the backbone hidden size. We primarily report nDCG@10, together with gener- ated tokens, average reasoning steps, and matched- setting wall-clock latency. 4.4 Baselines We organize baselines into three categories accord- ing to whether inference-time reasoning is used and how reasoning is integrated with retrieval. Setting I evaluates standard retrieval systems without explicit inference-time reasoning, where representations are constructed directly from the original query.
