To deliver strong performance across this diversity, we integrate performance enhancements into hipBLASLt [29] GEMM kernels through its assembly backend, TensileLite [30]. These enhancements leverage new CDNA 4 [31] hardware capabilities alongside algorithmic refinements that reduce the solution space and enable finer- grained runtime parameter selection via Origami (Section III-B). Beyond exploiting new ISA features, we employ the following algorithmic techniques. Stream-K partitions GEMM computations across CUs at finer granularity than traditional data-parallel tiling, improving load balance for tensor sizes that do not evenly tile the device. We also introduce new reduction strategies and runtime dispatch logic, improving robustness across a broad range of compute- and memory-bound tensor sizes. Notably, a single GEMM kernel can now achieve performance previously requiring multiple specialized kernels. Workgroup mapping via space-filling curves. MI350X GPUs use a multi-XCD architecture in which workgroups are dis- tributed across XCDs, each with a private L2 cache. Scheduling workgroups operating on adjacent or overlapping tiles across different XCDs degrades cache locality and efficiency. To address this, hipBLASLt introduces a mapping strategy based on space-filling curves that preferentially co-locates workgroups processing nearby tiles on the same XCD, improving spatial lo- cality, cache utilization, and power efficiency. Multiple mapping strategies are supported within the GEMM assembly kernels, with runtime-selectable parameters integrated with Origami to select the optimal strategy for a given tensor size, kernel configuration, and target hardware. B. Origami: Analytical Kernel Selection Prior kernel selection approaches in hipBLASLt relied on offline autotuning: enumerating kernel configurations on repre- sentative tensor shapes and storing the best selections in lookup tables. This approach fails at scale: recommendation models execute thousands of unique GEMM shapes per model, and maintaining exhaustive databases for every shape is impractical. Origami replaces offline autotuning with an analytical per- formance model that predicts optimal tile configurations in microseconds. The model can be viewed as inferring the critical path of a GEMM problem across the memory and compute hierarchy. It captures the full tiling hierarchy—from matrix instruction dimensions through local data share (LDS) tiles to implicit cache tiles formed by workgroups sharing the L2 and last level cache (LLC)—and computes cycle counts geometrically at each level. Performance Model. We consider a GEMM operation C = A × B, where A ∈RM×K, B ∈RK×N, and C ∈RM×N. To efficiently execute this operation on the GPU, the output matrix C is partitioned into tiles, each computed by a workgroup. A workgroup iterates along the K dimension, loading tiles of A and B, performing multiply-accumulate operations, and writing the result back to global memory. The goal of the performance model is to select the tile configuration (MT , NT , KT ) that minimizes total execution latency. For each candidate tile configuration with LDS tile size (MT , NT , KT ), Origami computes cycle counts for compute and memory operations, then selects the configuration minimiz- ing total latency. The compute latency for one tile is: Lcompute = NMI · LMI (1) where NMI = ⌈MT /MI⌉· ⌈NT /NI⌉· ⌈KT /KI⌉is the number of matrix instructions per tile (macro tile dimensions divided by instruction dimensions) and LMI is the architecture-specific instruction latency. Memory latency is computed by cascading traffic through the cache hierarchy. The bytes loaded per tile are: Bytestile = MT · KT · bA + NT · KT · bB (2) where bA, bB are bytes per element. Origami predicts cache hit rates by modeling workgroup sharing within each memory scope. For NCU CUs sharing a cache, arranged as an MC × NC grid of output tiles, the predicted hit rate is: H = 1 −MC · MT + NC · NT MC · NC · (MT + NT ) (3) This formula applies to L2 and LLC, with NCU set to the number of CUs sharing that cache scope. It captures data reuse: A tiles are shared across NC workgroups computing different output columns, while B tiles are shared across MC workgroups computing different rows. Tiles are rounded to the nearest cache line width in the contiguous dimension of the allocation (determined by transpose). The model constrains cache tile dimensions when working sets exceed cache capacity. Traffic reaching each memory level determines hierarchy latency. Bytes cascade through miss rates: BytesLLC = (1 − HL2) · Bytestotal and BytesHBM = (1 −HLLC) · BytesLLC, where each H is computed using the CU count for that scope. Expressing memory bandwidth in bytes per compute cycle keeps the memory and compute latencies in the same unit, so the model need not reconcile the GPU’s separate memory and compute clock frequencies. Issue Rate Bound. Effective memory throughput can be limited by the rate at which CUs issue loads and stores, not just bandwidth. This creates another parallelism-locality tradeoff on what are usually considered bandwidth-bound problems: smaller tiles increase the number of vector lanes issuing load/store requests but reduce data reuse, while larger tiles improve locality at the cost of issue rate. Origami models achievable throughput as a function of occupied vector lanes to navigate this tradeoff. Latency Model.
