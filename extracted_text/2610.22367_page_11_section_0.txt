11 Cost model and scoring We define the TQ-cost of a circuit by TQ = Toffoli count × peak qubit count, (22) where T counts Toffoli and CCZ gates equally and Q is the largest number of logical qubits allocated at once. We weight space and time equally in this cost function for simplicity. In practice, their relative importance depends on the hardware and application. When qubits are scarce, for example, a cost of the form (qubit count)κ ×Toffoli count with κ > 1 may be more appropriate; resource estimates for factoring have used κ between 1 and 3 [6, 30]. Either T or Q can also be replaced with other measures of time or space. In particular, when there is limited magic-state-factory throughput (as is typically the case), runtime is bottlenecked by the Toffoli count, motivating its widespread use as a time proxy [24, 25]. However, with enough factories to supply magic states in parallel, Toffoli depth rather than Toffoli count limits runtime. Similarly, for architectures with cheap cold storage for inactive qubits [31], Q can be replaced by active volume [32], which counts only the qubits participating in logical operations. The search is not tied to the specific form of the TQ-cost: it can run with any computable objective. A later case study illustrates the available trade-offs: the modular-inversion search (SI II) produces a family of circuits along a Toffoli–qubit frontier (SI II.1), and an objective that weights qubit count more heavily selects a lower-qubit member of that family. Evolutionary search We encode each candidate as Python code that constructs a circuit. Functions, loops, and named registers preserve the organization of the computation, allowing the LLM to reason about arithmetic subroutines and their composition without reconstructing that structure from a flattened gate sequence. For example, changing a shared arithmetic routine changes every place where it is used, while reorganizing calls to that routine can change when intermediate values are computed, retained, and uncomputed. The representation thus makes coordinated changes expressible as revisions to the underlying algorithm. We search over these circuit-generating programs with OpenEvolve [33], using Claude Mythos 5 [28] to propose architectures and program rewrites. Each of the eight searches uses a fixed, hand-written task specification, and all share the same generic circuit-building interface. During ideation, the LLM receives only the specification, circuit model, and correctness criteria, and proposes several distinct circuit architectures. The LLM has no access to the evaluator beyond the feedback returned after each submission. Starting from a blank program, it chooses the algorithm, representation, and circuit structure and produces the discovered circuits without substantive human intervention. Each architecture proposed during ideation founds a separate family of candidate programs. Later iterations improve descendants of the first working implementation. Keeping the families separate at first gives each approach time to mature, even if its earliest circuits are less efficient than those based on another approach. Periodically, leading programs are shared across families, allowing successful ideas from different approaches to combine. The search retains candidate programs and their evaluation results, tracking which family each belongs to and which earlier program it was derived from. It also saves feedback on failures and short notes in which the LLM records useful insights. These programs, results, and notes carry information between iterations; the sessions do not share a continuously growing conversation. Each iteration starts a new LLM agent session with the task specification, a parent program to improve, and its evaluation feedback. The agent also receives alternative programs from the archive and their resource costs, brief summaries of earlier attempts, and recorded insights where available. This context is limited; the agent never sees the complete search history. Within the session, it may rewrite the program, run drafts on test inputs, query a classical oracle for the required function on chosen inputs, and use the results to revise its design. It may also delegate focused subtasks to subagents. The iteration ends with submission of a revised program. The evaluator rejects a circuit that does not meet the task specification; a valid one is scored by its TQ-cost and considered for retention in its family. Thus the LLM is free to propose broad changes without having to judge their correctness: the evaluator supplies an independent test of every completed design. Extended Data Figure 1 shows the ideation and rewrite calls and a concrete feedback-and-repair cycle for a small finite-field inversion task. To decide which valid candidates remain available within each family, the search retains circuits with different trade-offs between Toffoli count and qubit count. We implement this selection with MAP-Elites [34], which divides the (T, Q) resource plane into cells and keeps the circuit with the lowest TQ-cost in each cell. A space-efficient circuit can therefore remain available for later development even when its higher Toffoli count gives it a worse TQ-cost. Because the families preserve alternatives, progress need not be monotonic in either resource. The Gaussian lineage in Extended Data Figure 2, for example, contains descendants that temporarily worsen Toffoli count or qubit count before reaching a region of lower TQ-cost. We report the lowest TQ-cost reached across all families at the end of the search.
