The task sampling weight is then computed with a Gaussian kernel, wi = exp  −(ˆpi −µ)2 2σ2  , We set the target success rate to µ = 0.5 and the bandwidth to σ = 0.25. Thus tasks with very high or very low estimated success rates receive lower weights, while tasks near the target success rate are sampled more often. To control visual-context length, we use a bounded sliding-window strategy. Each rollout maintains a history of 5–10 screenshots. When the history exceeds 10 screenshots, we save the current stream as a training segment, discard the five oldest screenshots, retain the five most recent screenshots, and resume collecting observations. Only assistant responses generated while the retained screenshot history lies in this 5–10 range contribute to the loss. Earlier context tokens are retained only as conditioning information with loss mask 0. Rewards come only from the paired environment evaluator, env.evaluate. We do not use auxil- iary format rewards or handcrafted step-level rewards. For valid trajectories and segments, evaluator scores are real values in [0, 1]. If an assistant response contains an unparsable tool call, an action outside the allowed schema, or another invalid action-format failure, that response is extracted as a separate invalid sample and assigned reward 0, even if the remaining trajectory could otherwise ob- tain a positive task-level score. This prevents malformed actions from receiving accidental positive credit through later recovery. D EXTRA EXPERIMENTS D.1 TRANSFER TO WINDOWSAGENTARENA Table 12 reports additional results for the 27B backbone and its corresponding OS-Helix variants on WindowsAgentArena, providing evidence of transfer from the Ubuntu-based training setting to this Windows benchmark. We retain the GUI and Hybrid baselines from the main experiments to preserve the same comparison between action-space access and learned hybrid behavior. Of particular note, since the operating system environment is Windows, we restrict Code actions to Python only, excluding the use of Bash. When Cmd/PowerShell commands would otherwise be required, system calls are instead issued directly within Python; this adaptation is implemented via prompt revision. Despite the absence of Windows-specific training data, OS-Helix improves on this benchmark. The SFT-only OS-Helix-27B raises the matched GUI backbone from 40.82% to 57.95%, a gain of 17.13 absolute points, and the RL variant reaches 63.87%, exceeding the GUI baseline by 23.05 points and the Hybrid baseline by 7.46 points. The unadapted Hybrid baseline also improves substan- tially over GUI (56.41% versus 40.82%), while OS-Helix-27B adds a further 1.54 points. These comparisons provide benchmark-specific evidence that learned GUI/code routing transfers to Win- dowsAgentArena under the reported Python-only prompt adaptation. The remaining gap is also diagnostic. Manual inspection of failed WindowsAgentArena trajec- tories shows that OS-Helix-27B often identifies the correct high-level strategy but can fail in the concrete system-command layer, mixing Bash-like patterns into Windows execution or producing brittle PowerShell-style logic despite the Python-only prompt adaptation. This pattern is compatible with the absence of Windows-specific command data. In contextual comparisons reported on the same benchmark, OS-Helix-27B-RL slightly exceeds OS-Symphony w/ GPT-5 and Agent S3 w/ GPT-5 under the shared 50-step budget. These results motivate scaling the synthesis pipeline along the operating-system dimension and evaluating on broader Windows and macOS task distributions. 28
