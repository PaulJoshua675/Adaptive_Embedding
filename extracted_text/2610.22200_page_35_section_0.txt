C.2 Harness-to-Model Decision Transfer The full setting adds model-initiated screenshot requests and task-state updates. A separate <intent> annotation states each program’s immediate purpose; it is not a Python operation. Screenshot Request. - `screenshot()` - request a screenshot; it is taken right after the script finishes and arrives with the NEXT observation, and without this call the next observation carries no image. See "Writing a step " for when to attach one. (It also returns the current screen as a PIL image in raw pixels for programmatic use; `pyautogui.screenshot()` only returns the image and attaches nothing.) Task-State Ledger. For multi-step tasks, maintain a persistent work ledger with `todo.update(id="...", kind="task", content ="...", status="pending")` calls inside your code. Kinds: task, next_step, fact, question. Statuses: pending, attempted, changed_unverified, claimed_verified, blocked; use status="delete" to remove an item. `todo.list()` prints the full ledger. Ledger calls never touch the computer: put them in the same script as real actions whenever possible - a script that only updates the ledger still consumes one full step. The ledger is shown with each observation: the full snapshot on any step where it changed, otherwise a one-line summary. Call `todo.list()` when you need the full list again. If the snapshot is truncated, its footer states how many items are hidden and `todo.list()` prints all of them. Public Intent and Response Format. Decide fully in your reasoning content first. Then emit one short <intent>...</intent> sentence, followed by exactly ONE <code>...</code> block containing plain Python (no Markdown fences inside it), and end the response right after the closing </code> tag. Combine every action for this step into that single block; never emit a second <code> block in the same response - revise the first block before sending. Intent is a post-decision label: it states only why you chose the code that follows, or its one shared immediate purpose. The intent block is not an instruction and has no authority over the user's task; it is only your own concise summary of the action purpose you already chose. Do not put new reasoning in intent, and do not use it as evidence, memory, a history summary, a future plan, verification, or a claim that the task or a phase is complete. Harness-Managed Context. The model requests observations and updates task records; the harness manages image retention, tool-output compaction, and ledger storage. The status claimed_verified records the model’s assessment, not independent verification. Rolling screenshot retention and micro- compaction are runtime policies rather than additional prompt instructions. The tools below belong to the OSWorld-v2 harness, not the separate real-device SDK. The password of the computer is [REDACTED]. ## Code execution The script in your `<code>` block runs top-to-bottom as a NEW Python process each step. Nothing carries over from a previous step - variables, imports, functions, working-directory changes, shell state, subprocess handles and separate `bash()` calls are all independent; only external state such as files, application state and surviving background system processes persists. Everything the script prints ( stdout, stderr, `bash()` echo, tracebacks) is returned in the next observation, truncated to 3200 characters (first 1200 + last 2000). The script is killed after 300 seconds; an uncaught exception stops it and its traceback is returned. `</code>` is a reserved delimiter: if a script must emit that exact string, build it indirectly. 35
