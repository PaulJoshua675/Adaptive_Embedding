After all candidate histories are generated, a second pass groups jobs by employer: any employer with at least two employees receives a roster document and a roster chunk listing every employee and title, which mentions the organisation and each employee individually. The same employment fact therefore appears both in a person’s job chunk and in an employer’s roster chunk, so information about one entity is distributed across documents connected only through shared entities. This is what makes the corpus suitable for graph-retrieval experiments rather than reducible to independent flat documents. Schema. The graph is a plain JSON dictionary with three node types and three edge types. Every node exposes an embed_field naming the field embedded at ingest: name for entities and documents, text for chunks. The graph itself is therefore not embedded during generation. Category Type Semantics Node entity Person or organisation Node document Resume or roster Node chunk Textual evidence Edge part_of Chunk →document Edge about Document →entity Edge mentions Chunk →entity For each person the generator creates an entity:person:<Name> node and a document:resume:<Name> node joined by about. Every education, job, project, endorsement, and certification record becomes a chunk, linked to the resume by part_of and to the person by mentions. Educa- tion chunks also mention a university entity and job and project chunks an employer entity; organisation nodes are created on first use and reused thereafter. Identifiers are deliberately human-readable—entity:person:<Name>, chunk:job:<Name>:<i>—and these are the canoni- cal evaluation identifiers, preserved downstream in the vector store and in the result artefacts. The schema admits exactly three edge patterns and no others, so the graph is tripartite. One hop from a chunk reaches the entities it mentions and the document it belongs to; two hops return to other chunks through a shared entity.
