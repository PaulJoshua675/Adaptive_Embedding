E.2 SFT Configuration Table 16 details the SFT hyperparameters for both model scales. We report only parameters that affect the optimization objective or its trajectory; sharding strategy, device place- ment, and accumulation factors are implementation choices that follow from the global batch size and are omitted. Three choices warrant comment. Loss masking: gradi- ents are computed only on assistant-generated tokens; tool results, file contents, and test output are supplied as context but excluded from the objective, since these constitute envi- ronment observations rather than target behavior. Sequence length: the 131,072-token window matches the generator’s context budget, so no retained trajectory is truncated during training; training at this length uses sequence parallelism. Learning rate: with only 2,304 trajectories, the corpus is small enough that the higher end of the search range overfits within one epoch. Qwen3.5-35B-A3B activates roughly 3B parameters per token, so its optimal rate is close to—though slightly below—that of the 4B dense model rather than an order of magnitude lower. Both scales use identical batch size and epoch count so that the controlled comparison in RQ3 varies only task con- struction. The resulting schedule is 144 optimizer steps per epoch and 432 steps overall, of which the first 13 are warmup. All runs use a single fixed random seed; reported results are single-run unless stated otherwise. Data mixing strategy. For controlled comparisons, we en- sure matched token budgets across all data sources: • Each training arm uses ∼158 M tokens. • For external references (SWE-rebench V2, daVinci- Agency), we sample trajectories uniformly to match the token budget. • For controlled variants (Atomic-PR, Temporal-Window, WEAVE), trajectories are generated from the same repos- itory pool using the same generator and quality filter, differing only in task construction. • All variants use identical SFT configuration (Table 16). Checkpoint selection. We select the final checkpoint by Graph Credit on a held-out calibration set of 50 tasks disjoint from WEAVE-Bench, evaluating every 36 steps (one quarter epoch) for 12 evaluation points across the 432-step schedule. E.3 RL Configuration Table 17 details the GRPO configuration for RQ4. Unlike SFT, RL requires no gold trajectory—only an executable environment—so the prompt pool is the full WEAVE-Train set of 3,200 tasks rather than the 2,304 tasks for which a demonstration survived filtering. We specify the interaction budget in terms of the quantities that define it—pool size, group size, tasks per update, and passes over the pool—and report the induced update and episode counts as derived values, so that the budget can be reconstructed exactly. Both scales share the same interaction budget so that the reward comparison in RQ4 is not confounded by differing amounts of experience. The rollout temperature of 1.0 is de- liberate: GRPO derives its advantage signal from variation within each group of G rollouts, so insufficient sampling diversity collapses the group to a common reward and con- tributes no gradient. Reward coefficients. The reward RWEAVE uses the fol- lowing coefficients (selected via grid search on calibration set): • λgraph = 0.5 (dominant component) • λsolve = 0.25 (full-task bonus) • λf2p = 0.15 (flat progress) • λreg = 0.1 (regression penalty)
