A superseded snapshot may therefore remain resident while requests still hold references to it. Retired snapshots are reclaimed only after all request-scoped pins have been released. Cache-hit and miss-driven loading paths converge at the same ready-state boundary, so the request-visible semantics do not depend on whether the snapshot was already resident or fetched after admission. Continuation checkpointing and replay recovery. Encoder continuation state is checkpointed asyn- chronously together with its source cursor, represented-history cutoff, and compatible representation versions. Let 𝑐0 denote the source cursor recorded by the latest compatible checkpoint and 𝑐the current committed source position. Recovery reconstructs current continuation state by restoring the checkpoint and replaying the retained behavior-log suffix: 𝐶(𝑢) (𝑐0) + Δ𝐻(𝑢) (𝑐0, 𝑐] −→𝐶(𝑢) (𝑐). Source retention is configured so that every acknowledged behavior update is either represented in a durable checkpoint or remains available for replay. Recovery reconstructs mutable continuation state 𝐶; it does not invalidate an already published compatible behavior memory snapshot 𝑉. Consequently, online requests can continue to consume the latest admissible published state while checkpoint restore and log replay proceed asynchronously. Once continuation state catches up, ordinary nearline advancement resumes and a fresher behavior memory snapshot can be published. Pipelined nearline execution. Nearline workers overlap continuation-state access, incremental encoding, memory construction, snapshot persistence, and publication across independent users. State required by a future update may be fetched while another update executes, while completed behavior memory snapshots may be persisted and published as subsequent encoding work proceeds. This pipeline hides a portion of state-transfer and storage latency without relaxing causal ordering of committed state transitions within a user. B.2 Large Sparse Embedding Serving The sparse embedding tables need not reside entirely in accelerator memory. TransX exposes one versioned embedding namespace but uses different placement and lookup paths for bulk prefill, nearline prefill, and online prediction, as summarized in Table 13. Small tables may be replicated in HBM within the serving-memory budget. Larger tables use sharded backing storage, with GPU and host caches retaining selected rows. Inference placement is chosen independently of the training sharding plan because serving has no gradient traffic and substantially different locality and latency requirements. Each operation pins a compatible model and embedding version before lookup; deduplication and cache reuse never cross incompatible versions, and reused continuation or behavior memory state must be compatible with the corresponding producing parameters. Candidate batches are dispatched to cross attention kernels only after all required embedding rows are resolved. Pending lookups still consume queue, buffer, and transfer resources, which are bounded separately. A behavior-memory hit removes historical re-encoding from the online serving path, but request- and candidate-side embedding lookups may remain. A cache miss for a known row triggers retrieval, not substitution with an unknown-ID vector. Legitimate unseen IDs follow the model’s declared OOV policy, while unavailable or incompatible rows follow an explicit failure policy. In particular, prefill does not publish behavioral state constructed from temporary cache-miss defaults. 59
