With batched actions, each model call yields a list of actions that were fixed when the call was generated: the model must decide every click before it sees the result of the first one. With code execution, each model call yields a program, and control flow is decided while the program runs. Three things become possible in a single call that were impossible before: a condition (if the dialog is visible, dismiss it), a loop (for each row, fill the three fields), and a verification (assert the status now reads Saved). A task that took a dozen round trips becomes one. This is also why batched actions, which our earlier work introduced (Zhou et al., 2026), are a stepping stone rather than an endpoint: a batch is a program without control flow. 2.4 Efficiency as a First-Class Metric Success rate remains our primary measure, but it does not capture the resources required to complete a task. For interactive tasks, an important threshold is reached when delegation delivers results sooner than manual execution, potentially saving both human effort and time to completion. We therefore evaluate efficiency using four metrics: steps per task, output tokens, reasoning tokens, and cost. Each step is one model call, which may generate multiple actions through batching or code execution. Fewer steps reduce model-call overhead, while fewer output tokens can lower generation time and cost. Reasoning tokens are included in output tokens but reported separately. When reasoning accounts for a large share of output, reducing unnecessary reasoning can improve efficiency without shortening the executable code, provided task performance is maintained. We compute cost from input and output token usage at each model’s published prices, including cache discounts. 3 Agent Design: Code Execution and Harness-to-Model Decision Transfer This section studies two behaviors we aim to develop in GCUA models. The first is code execution, which concerns how to act: the model combines graphical interaction and programmatic operations within a single program. The second is harness-to-model decision transfer, which concerns what to observe and how to organize: the model makes selected workflow control decisions that a harness would otherwise fix with rules, such as when to look at the screen and how to organize task state. This release does not introduce a trained model. Instead, we study how the prompts, tool interfaces, and execution runtime of Open Generalist CUA support these behaviors in existing frontier models. We first explain the design and illustrate it with execution trajectories, then evaluate its effects on task completion and cost. 3.1 Code Execution over GUI and CLI Code execution gives graphical interaction and programmatic operations a unified executable form. The model writes a program in which GUI actions, such as pyautogui.click(), can be combined with shell commands and Python computation. The model can therefore specify not only what operations to perform, but also how execution should proceed. Loops and conditional logic allow the program to repeat operations and choose subsequent actions based on intermediate results, without requiring a new model call for each operation. On OSWorld-v2, this design improves Qwen3.8-Max’s mean task score by 5.2 points and reduces steps per task by 17.0% relative to a hybrid CUA baseline with batched GUI+CLI actions (Section 3.3). 3.1.1 Implementation Prompt Design.
