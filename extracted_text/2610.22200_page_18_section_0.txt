For example, an agent inspecting a background product page may receive an unrelated login page if it requests a desktop screenshot rather than an image of the selected tab, as illustrated in Section 4.3.4. Observation and control also impose different requirements. Being able to inspect a background target does not imply that every operation on it can run in the background. The model must select a supported control method, while the harness makes target identities, available capabilities, and foreground-input requirements explicit. Observations and actions should remain tied to their selected targets rather than silently following changes in desktop focus. These requirements link the model’s observation and action choices to the resource bindings and capability declarations in the Cross-Device SDK (Section 4.2). Tasks begin in an existing user environment. Benchmark tasks typically start from a prepared state. A user’s computer instead retains files, open tabs, application windows, and account sessions from prior use. Relevant materials may be mixed with unrelated content or similarly named files, requiring the agent to identify the correct inputs before acting. Expired sessions or missing permissions may also require user involvement before execution can continue. These requirements mean that benchmark scores alone do not establish reliable operation on users’ devices. We therefore study real-device capability alongside benchmark performance, rather than treating deployment as an implementation detail. The following sections describe our SDK and harness, and Section 4.3.3 reports preliminary real-device results. 4.2 Cross-Device SDK A computer-use task may span a mobile application, desktop tools, and a browser-based service. The Cross-Device SDK provides a common programming interface through which one agent can coordi- nate these environments. It supports both the reuse of common operations across platforms and the composition of cross-device workflows within a single task.
