A.2 Questions and Gold Answers Each question is paired with an exact answer and with the evidence required to derive it. Generation is deterministic under a fixed seed and uses no language model: Python functions traverse the graph, read the structured fact preserved in a chunk’s source field, instantiate a fixed template, and record the nodes touched along the way. The generated chunk text is never parsed to recover an answer—text is what retrieval sees, while the structured record defines the ground truth. The stored record. Every generator returns the triple (q, Cq, aq), where q is the natural- language question, Cq is the set of graph nodes touched while deriving the answer, and aq is the answer computed from structured facts. Before persistence Cq is filtered to the evidence-bearing chunks, giving the gold-evidence set Gq, so each stored example is (q, agold q , Ggold q ). Why only chunks count as targets. Filtering keeps only nodes whose type is in GOLDEN_NODE_TYPES = ("chunk",). Entities named in the question are query inputs, not retrieval targets: the re- triever already has them. What it must recover is the text that carries the evidence. Rewarding a system for returning an entity the question itself names would measure nothing. Filtering happens at record-writing time only, and changes neither the question text, nor the computed answer, nor the sampling or reasoning depth. Question families. Eleven families span basic, compositional, and multi-hop reasoning. Basic families retrieve or aggregate local attributes, compare candidates, or select extrema; compositional families chain two basic operations and union their evidence; multi-hop families traverse explicit person–organisation–university relations over one, two, or three hops, alternating between two predefined chains at each level. Because every traversal step is recorded, the benchmark keeps the whole supporting chain and not only the node holding the final answer. 19
