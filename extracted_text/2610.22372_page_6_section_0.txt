The task language is also abstracted to cover both settings, ensuring that behavioral differences are driven by the preference rather than unrelated scene changes. Preference-Conditioned Subtask and Trajectory Generation. After the layout and task language are fixed, the pipeline uses a VLM with the task language and preference language to generate both a no-preference subtask plan and a preference-conditioned subtask plan. It then calls a library of pre-recorded heuristic skills to generate trajectory data. To construct each heuristic skill, we first collect one human demonstration for the skill, extract key waypoints, and use an OMPL planner [73] with randomized initial states to generate many successful trajectories. The generated trajectories are then smoothed; heuristic-skill parameters are manually offset-adjusted when needed. Empirically, we find more than 72% of skills require no offset adjustment across any task, suggesting the VLM-based edit is already very effective. Preferences are applied at different stages according to their type: User Profile affects subtask-plan generation via a prompt; Skill Preference affects skill selection, such as using pick_handle instead of a regular pick skill; and Motion Preference affects skill-level trajectory generation, such as reducing OMPL-sampled waypoints for the “speed up” preference. Satisfaction Metric Generation. After preference-conditioned trajectories are generated, the pipeline constructs explicit preference satisfaction metrics for each selected preference. The form of each metric depends on the preference type. For Motion Preference, we directly compute satisfaction functions from trajectory quantities, such as the distance between the robot trajectory and the target object for the preference “avoid certain object”. For Skill Preference, we evaluate key waypoints and use VLM-based image checks to verify skill-specific execution, such as whether the object is grasped by its handle. For User Profile, we monitor the executed subtask plan, including which objects are manipulated, to verify that the plan adheres to the profile. Because User Profile yields only discrete Satisfaction Scores, namely whether the profile-conditioned subtask is satisfied, whereas Motion Preference and Skill Preference can yield continuous Satisfaction Scores, we construct a mapping from Satisfaction Scores to Discrete Satisfaction Labels using trajectory statistics and human inspection; Appendix D details the review protocol. Specifically, each episode is mapped to a fixed four-level Discrete Satisfaction Label d ∈{0, 1/4, 3/4, 1}, independent of the number of pipeline-generated subtasks. A continuous Satisfaction Score, such as speed, is binned by trajectory statistics and then incorporated into this label. Raw Satisfaction Scores provide denser feedback for training, while Discrete Satisfaction Labels provide a more interpretable evaluation signal at inference time. Initial Human Validation. To assess the real-world plausibility of the selected preferences and the human-likeness of the generated demonstrations, we conducted a survey with 15 participants using a 10-point scale. Across all preference categories, the demonstrations received an average human-likeness score of 9.11, and the preferences received an average real-world plausibility score of 8.35. These results provide initial human validation of the benchmark design; Appendix D reports the protocol and category-level results. 3.3 Task Suites Using the pipeline above, we generate five task suites: LIBERO-SinglePref, LIBERO-PrefScale, LIBERO-PrefConflict, LIBERO-PrefCompose, and LIBERO-ComprePref. We follow LIBERO terminology and call the inseparable combination of a task instruction, scene layout, and task-goal condition a mission. A LIBERO-PeRM task pairs one mission with one preference condition, which may be a specified preference or no preference; the 312 tasks include both preference- conditioned and no-preference tasks (see Figure 2(b) for the proportions), with more than 100 trajectories per task on average and 40.8K rollout episodes in total. Randomized initial object positions, paraphrased instructions, and repeated executions increase rollout diversity but do not create additional tasks. The release prioritizes quality-controlled coverage over claiming the largest trajectory count; the procedural pipeline can extend it with more initial states and missions.
