Pooled contrasts are in Table 1. 5 Case Studies in Software Refactoring Software refactoring often requires applying a demonstrated transformation at multiple sites. For example, updating callers after extracting a helper requires adapting receivers, arguments, and surrounding code rather than copying an accepted edit. 5.1 Helper Refactoring Experiments We construct multi-site editing tasks from Extract Method commits in SWE-Refactor (Xu et al., 2026b). Each task includes the extracted helper, D accepted <old>/<new> demonstrations, and J masked replacement sites. We evaluate 127 tasks from 50 commits across 14 repositories, with (D, J) ∈{1, 2}2; different configurations have different eligible commits (Section C.1). Frozen LLaDA-1.5 (Zhu et al., 2026) generates K = 16 rewrites per task using either oracle lengths or lengths sampled from a separately trained Java predictor. We compare unguided sampling (β = 0) with example guidance (β = 0.5) on the same samples. We assess joint correctness using Claude Sonnet 5.5, without executing the generated code. A separate post-hoc ablation on 80 tasks compares generation with and without one visible accepted edit, holding the other prompt components and oracle lengths fixed. Adding the demonstration improves joint LLM-judged success by 14.7 and 17.5 percentage points for J = 1 and J = 2, respectively (Section C.2). These gains indicate that the DLM can use a demonstrated refactoring to guide edits at other sites. Under unguided sampling, pooled joint success reaches 74.4% with oracle lengths but only 15.8% with predicted lengths (Table 1). This gap identifies length allocation as a major opportunity for improvement, even though the predictor outperforms a simple length prior (Figure 8, left). Example guidance at β = 0.5 reduces success to 71.5% and 14.5%, respectively (Table 1). Thus, demonstrations help the DLM generate appropriate rewrites, but the additional likelihood-ratio reward does not improve their selection in this experiment. 12
