We define a GCUA by three decisions that its model makes at each step: what to observe, how to act, and how to organize its work. We show that GUI agents, CLI agents, multi-agent hybrids, and GUI+CLI agents such as Qwen-UI-Agent each fix some of these decisions in advance, and are special cases of GCUA (Section 2). • GCUA outperforms GUI-only CUA on every frontier model we test. We implement our GCUA agent design into the OpenGCUA harness, which lets existing models use code execution and harness-to- model decision transfer. We test it with eight frontier models, including GPT-6 Astra and Claude Opus 5. On the offline set of OSWorld-v2, the full GCUA setting raises the mean partial score by 19.6 points, cuts steps per task by 53.0%, and narrows the score gap between the strongest and weakest models by more than half. We release the implementation, prompts, and evaluation trajectories of all eight frontier models (Section 3). • Code execution adds value beyond shell access. With the same GUI and shell access, writing GUI operations as code and combining them with programmatic operations adds 6.1 points to the mean partial score and cuts steps per task by 14.8% against the GUI+CLI baseline. Code execution offers two advantages: intermediate results can decide the next operation without another model call, and models can bring their existing programming ability directly to computer interaction. We further identify five recurring patterns of code execution in our case study (Section 3.1). • Harness control should move into the model as models improve. Harnesses fix many workflow decisions by rule, such as taking a screenshot after every step. We propose harness-to-model decision transfer, which delegates these harness decisions to the model. In the current implementation, the model decides when to request screenshots and how to track task state. It also states each program’s purpose before execution. On-demand observation alone increases cache hit rates by 10.5 and 14.4 percentage points for two models without lowering task scores (Section 3.2). • On real devices, a large gap lies in the model. We release a preliminary real-device harness for users’ own computers, addressing challenges unseen in benchmarks, such as sharing the machine with its user and acting on background windows. With the harness held fixed, Qwen3.8-Max uses 19.4 times as many reasoning tokens as GPT-6 Astra on four real macOS tasks, and 5.7 times as many output tokens in total. Case studies trace this gap to model behavior: large reasoning cost for simple operations, difficulty adapting to real-device conditions and a gap in code execution capability (Section 4). 4
