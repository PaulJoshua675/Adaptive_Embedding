The prompt requires one Python program in a <code> block per step and includes examples that combine interface operations, shell commands, and checks on intermediate results. The full prompt is given in Appendix C. Program Execution. The harness extracts and syntax-checks the code block, then executes it in the computer environment. The runtime supports desktop interaction through PyAutoGUI and, in the real-device harness, browser interaction through Playwright. Shell commands execute through bash(), which returns command output and exit status. The Python control flow coordinates these calls, allowing loops and conditions to combine GUI and shell operations within one program. Execution Feedback. The harness returns captured standard output, standard error, and execution status to the model. With on-demand observation enabled, observations include a new screenshot when the program requests one through the screenshot() action. The real-device harness additionally returns accessibility-tree observations when requested by the model. We have open-sourced both the preliminary real-device harness and the code execution harness. 3.1.2 Representative Code-Execution Patterns The implementation specifies what a program can contain, but we want to see how models actually write programs to solve concrete tasks. We therefore examine GPT-6 Astra on OSWorld-v2, and find five recurring patterns in how its programs connect actions, intermediate results, and model observations. The examples illustrate complementary uses of code, rather than mutually exclusive categories or isolated performance gains. Cross-Interface Composition. A single program can use information from one interface to guide operations through another. A program can alternate between GUI actions and programmatic checks within one model step. In a contract-generation task, the agent clicks a spreadsheet button, reads the application’s completion status, and checks the output files. Only after these checks pass does it click a second button to create local email drafts, which it then inspects programmatically. This example connects GUI execution with structured feedback from both the application and its files (Figure 3a). Loop-Based Execution. Loops let the model specify a procedure once and repeat it across multiple targets within one program.
