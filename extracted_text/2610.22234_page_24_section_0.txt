To avoid repeatedly covering familiar functionality, we main- tain global application memory that records functions previously exercised for each applica- tion and expose it during subsequent exploration. When additional interface information is needed, the Exploration Agent may perform a short non-destructive inspection using only open, click, scroll, and done. Keyboard and free-form text input are unavailable to avoid mu- tating the known initial state. It then proposes a goal-oriented instruction and fine-grained suc- cess conditions for evaluator synthesis. The resulting instruction record contains fields such as snapshot, versioned related apps, instruction, config, complexity, category, success criteria, and evaluation requirements text. The instruction field is the core user-facing task specification. The snapshot, related apps, and config fields are determined during initialization and record the reproducible environment context. The category field is generated by the Exploration Agent together with the instruction and is divided into three groups. app only denotes tasks centered on application or system functionality, such as chang- ing software or user settings. file only denotes tasks centered on processing input files whose final deliverables are file artifacts. mixed denotes tasks that involve both. The complexity field estimates the length of a pure-GUI solution. We label tasks with 5–15 steps as easy, tasks with 15–40 steps as medium, and tasks with more than 40 steps as complex. The success criteria field lists the terminal conditions that must hold after successful task com- pletion. The evaluation requirements text field translates those conditions into concrete checks for evaluator synthesis, such as which file, slide, field, format, or application state should be inspected. The instruction states non-answer constraints such as locations, scope, ordering, quan- tity, format, and filenames. Exact observed values are retained only in these hidden success and evaluation fields. Evaluator synthesis. Evaluator synthesis begins only after an instruction proposal has been ac- cepted and is performed by an independent Evaluator Agent in a separate context. Its inputs are the frozen instruction fields, initialization configuration, success criteria, and textual evaluation re- quirements. The Evaluator Agent may generate only the verification specification and cannot revise the instruction or proposal metadata. A rule-based evaluator comprises one or more self-contained Python judge functions.
