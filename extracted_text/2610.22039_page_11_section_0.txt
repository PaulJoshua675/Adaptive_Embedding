A.2 Edge Filtering and DAG Assembly Mechanical-change filtering. Not all PR pairs with high coupling scores reflect genuine engineering dependencies. Certain repository maintenance patterns produce mechani- cally related patches that inflate coupling metrics without meaningful task structure. We identify and remove four cat- egories before DAG assembly: • Reverts: PR pj is identified as a revert of pi via two complementary signals: (i) title-level patterns (Revert "...") and (ii) content-level detection where the diff of pj is the near-exact (≥95% line overlap) inverse of pi’s diff. • Backports and cherry-picks: PRs explicitly labeled as cherry-picks or backports (via commit message mark- ers or branch metadata) to release branches represent the same logical change applied across code states. • Release-branch references: PRs whose title or body ref- erences release, stable, maintenance, or hotfix branches (detected via text patterns such as release/, stable/, maint/, hotfix/) are removed, as they typically represent integration merges rather than incre- mental development. • Near-duplicate patches: PR pairs with high file-set over- lap (Jaccard ≥0.8) and high containment (≥0.9) indi- cate template-generated or copy-paste changes rather than incremental development. Across our construction corpus, backports and cherry-picks dominate the filtered set (>95%), as multi-branch workflows frequently produce mechanically identical patches across re- lease channels. Reverts, release-branch references, and near- duplicate patches each contribute a small fraction of the re- mainder. Component partitioning. After edge filtering, the remain- ing edges within each repository induce connected compo- nents. We process these components as follows: • Components with |V | ≤K (where K = 8) are retained as complete candidate DAGs. • Larger components are reduced via greedy subgraph ex- traction: we iteratively select the highest-weight con- nected subgraph of size ≤K by starting from the densest node (highest sum of incident edge weights) and expand- ing via best-first search. Extracted subgraphs are removed from the component, and the process repeats until no sub- graph of size ≥2 with mean edge weight ≥θ remains. Node budget. The budget K controls the maximum num- ber of PR nodes in a single task. We set K=8 based on two considerations. First, rollback feasibility: constructing executable in- stances requires reverting all constituent PRs from the repos- itory’s integrated state (§A.3). In our corpus, the median merge-time span (first PR to last PR) is 51 days for K=4 tasks and 78 days for K=8 tasks. Although larger K does not monotonically increase span—K=8 chains are often dense feature or migration bursts with short inter-PR intervals (∼10–15 days), while smaller chains can span longer periods with sparser commits—the absolute span at K=8 (median ∼2.5 months, range 17–332 days) means the repository accu- mulates substantial intervening changes from outside the task scope, raising the probability of non-trivial merge conflicts during rollback construction. Indeed, approximately 35% of candidate DAGs are discarded during construction (§A.3). Second, ecological validity: coherent engineering objec- tives in open-source repositories—feature additions, system- atic refactors, dependency upgrades—rarely produce more than eight tightly coupled PRs before coupling evidence be- tween peripheral changes falls below the detection thresh- old. In our candidate pool, connected components exceeding 8 nodes predominantly arise from hub-file co-modification (shared configuration, CI pipelines, or utility modules) rather than focused development objectives. This observation is consistent with prior work on software change coupling, where meaningful change sets typically span 2–6 related commits. The resulting benchmark reflects this design: WEAVE- Bench tasks range from 2 to 8 PR nodes (mean 4.91, median 5), with a broad distribution across this range, spanning the full complexity spectrum from simple linear chains to deep branching dependency structures. Algorithm 1 summarizes the complete pipeline from typed change loci extraction through bounded DAG assembly. DAG orientation. All edges are oriented by merge times- tamp: if pi was merged before pj and the coupling score exceeds θ, the edge is directed pi →pj. This temporal ori- entation reflects the incremental nature of software devel- opment without requiring explicit dependency annotations from developers. Cycles (which would arise from conflicting timestamps in rebased histories) are broken by removing the lowest-weight back-edge in each strongly connected compo- nent.
