The planner decomposes the prompt into named parts with metric bounding boxes, materials, attachment relations, and an acceptance checklist; each target maps to its owned source files, and refinement tasks sharing files are grouped into file-disjoint sessions. In Round 1, nine revision tasks partition into eight file-disjoint groups; in Round 2, four tasks form four groups. Bounded plan verification. Planning executes as a structured-output call with a token budget scaled to the target part count. Range or formatting violations are repaired in-context, whereas a degenerate kinematic hierarchy referencing undeclared links triggers a clean context reset from the original request (§C.5). File-scoped subtree decomposition. Each runtime maps plan targets to strict file-ownership scopes (per-part modules plus an assembly entry file for Blender and Three.js objects; a single program for CadQuery, URDF, and graphics; and per-zone and per-asset modules for scenes), and writes outside a session’s scope are reverted between Git commits. Objects with eight or more top-level parts in modular languages are synthesized via scoped sessions over attachment subtrees of at most three parts—each supplied with the planned bounding boxes of adjacent parts—followed by an assembly session (Figure 8). During refinement, tasks that share files are grouped into connected components and dispatched as file-disjoint sessions, bounding per-session context and preventing cross-part regressions (§C.5), while best-of-N candidates and scene assets run concurrently in isolated workspaces. Session context and contract injection. Every agent workspace is provisioned with a standardized instruction specification containing the runtime invariants, track-specific tool schemas, and language contracts. Each task prompt supplies the user request, coordinate-frame conventions, the language cookbook, the structural plan formatted as exact metric tables with its acceptance checklist, and the verification protocol (requiring a clean build followed by spatial measurement or probing). Single-shot prompts inline the code skeleton and request a complete file envelope in a single response. A.3 SPATIAL TOOLS AND DETERMINISTIC GATES Semantic verdicts vs. transport errors. Every tool response separates the semantic verification verdict (PASS/FAIL) from the tool execution status. A detected mesh collision or build failure is returned as a valid observation leading with a structured FAIL verdict; only an internal tool crash sets the MCP protocol error flag, preventing commercial coding agents from entering degenerate transport-retry loops (§C.5). Tool responses bound text length and image resolution, attaching diagnostic renders specifically when a check identifies actionable geometric defects. Deterministic gates, connectivity, and plan adherence. Following each successful build, the track pipeline executes its deterministic gates.
