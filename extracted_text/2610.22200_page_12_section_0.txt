The examples come from GPT-6 Astra trajectories on OSWorld-v2. They illustrate the mechanisms, not their individual effects on task success. Requesting Visual Feedback Only When Needed. In a calendar task, the model checks saved events and calls screenshot(). Its next input contains text output and a new screenshot. The following program inspects event styles without requesting another image, so the next input contains text feedback but no new screenshot. These adjacent steps show the observation decision: the model can request visual input or continue with programmatic feedback. Earlier screenshots may still remain in context. Keeping Unfinished Work Explicit across Programs. In a form-filling task, the model records that all fields have been entered but submission is still pending. It marks the task changed_unverified. After a later program clicks Submit and reads the page’s confirmation, the model updates the same record to claimed_verified. The persistent record distinguishes work performed from an outcome checked. Its status remains the model’s assessment, not an independent evaluation. Stating a Program’s Purpose before Execution. In a CRM task, one intent statement summarizes a 64-line program: update 29 lead statuses while preserving the original customer details. The program performs status-only updates and checks other fields, allowing modification timestamps to change. The <intent> block makes both the intended change and the preservation requirement explicit without requiring the reader to reconstruct them from the code. 3.3 Experiments on Agent Design We evaluate whether the agent design presented in this report helps frontier models complete computer tasks more effectively.
