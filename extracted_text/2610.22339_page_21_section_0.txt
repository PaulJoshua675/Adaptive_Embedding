LEANGRAPHSEARCH evaluation. The same reasoning prompts are used to prepare the initial context for theorem proving in Reasoning Mode. Reasoning retrieval follows four stages: planning, retrieval, filtering, and route assessment. The planning prompt first seeks high-level theorems that may directly advance the proof, then key def- initions and lemmas for individual steps, with at most 20 queries across all categories. For each query, a filtering prompt examines up to 50 declarations and selects results according to their mathe- matical relevance, Lean types, and intended role in the proof. The filter may return an empty list. A judge assesses whether the filtered premises support an implementable Lean proof route and returns a good or bad judgment with feedback. This judgment evaluates the proposed route; successful theorem proving still requires Lean verification. Two reasoning branches run in parallel, each allowing an initial plan and up to three revisions based on judge feedback. The first branch judged good supplies the final route. If neither branch is accepted, their final filtered lists are pooled and declarations are ranked by the sum of their position- discounted contributions across queries. The resulting list contains at most 100 declarations. Theorem proving. Standard Mode begins with a proof attempt without retrieved context. Reason- ing Mode first obtains a proof sketch and filtered premises through the reasoning procedure above. After a failed attempt, both modes permit reflection-time retrieval: the query prompt receives the theorem, the preceding tactic body, and the compiler feedback, and requests exactly five comple- mentary natural-language queries. The next proof attempt is conditioned on the previous attempt, compiler feedback, and deduplicated retrieval results. There is no separate initial-query generation step outside the reasoning procedure. The proof-generation prompts supply an immutable theorem prefix and suffix and request a complete replacement tactic body. Shared proof-integrity instructions require the prover to establish the target from its hypotheses and existing library declarations, with any auxiliary results proved locally. The generated body is inserted into the fixed source context and checked for source integrity before Lean verification. Source-integrity errors and Lean diagnostics are returned as feedback for the next revision. Failure memory. Failure memory is used only in theorem proving. When enabled, its guidance is included in the initial proof prompt and every revision prompt, while the memory itself is initially empty. After a failed attempt, a structured failure summary is appended to the compiler feedback and is therefore available to both proof revision and reflection-time query generation. The summary records recurring formal states, occurrence counts, and unsuccessful tactic or declaration appli- cations. An unchanged candidate with a cached deterministic failure is blocked without another compilation. D.2 DECODING AND SEARCH BUDGETS Model settings. Gemini 3.1 Pro with HIGH thinking is used for all proving runs and one Math- libMPR retrieval run. Requests set top p to 1 and cap model output at 65,536 tokens. Temperature is left at the provider default, and Google Search is disabled. The second MathlibMPR retrieval run uses Claude Sonnet 5 with adaptive thinking, high effort, and a 128,000-token output cap. Its tem- perature and top p remain at the provider defaults, and no sampling seed is supplied. Each paired comparison uses the same model settings and prompt templates. Retrieval budgets. All retrieval calls in the retrieval and proving evaluations use K = 50 re- turned declarations, and LEANGRAPHSEARCH uses N = 200 PPR-ranked expansion candidates. Thus, the comparison uses the top 50 results from each retriever under the same per-query output budget. In MathlibMPR retrieval and initial reasoning retrieval for proving, each query supplies up to 50 declarations to the filter; the filtered lists are aggregated into at most 100 declarations. Each reflection-time retrieval action generates five queries with up to 50 results each, which are dedupli- cated before being passed to the prover. The larger internal candidate pool used by graph retrieval does not increase the per-query output budget. Proving budgets. A trajectory contains one initial candidate and at most 31 compiler-tested revi- sions. At most one retrieval action is available before each revision, for a maximum of 31 actions. 21
