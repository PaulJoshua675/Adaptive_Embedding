Loss numerators are accumulated over the globally valid supervised targets and the declared normalization is applied once at the logical update boundary. Likewise, all same-step gradient contributions to a dense parameter or sparse embedding row are combined before the corresponding nonlinear optimizer update. Sequence and fanout partitioning therefore change the physical execution graph, not the objective or optimizer semantics. The underlying parameter and embedding sharding use standard distributed primitives; the TransX-specific execution mechanisms are trajectory packing, multi-cutoff memory extraction, event-state ownership, and sequence–fanout scheduling. 5.3 Disaggregated Serving Figure 6. Disaggregated TransX serving. Offline and nearline workers maintain encoder continuation state and publish compact immutable behavior memory snapshots; online requests pin and consume only compatible behavior memory state. Continuation recovery remains off the online serving path, while snapshot residency and transfer are managed independently across GPU, host, and durable tiers. In practice, hardware placement can be made workload dependent as the three worker stages define logical execution roles rather than fixed device types (CPU/GPU). The amortization boundary induces serving workloads that operate on different clocks. Behavioral state must be constructed when a new model or representation is deployed, advanced when new user behavior arrives, and consumed when recommendation requests are issued. These workloads have fundamentally different execution objectives: bulk construction is throughput-oriented, incremental maintenance is freshness-constrained, and online prediction is latency-critical. Co-locating them under one scheduler would couple workloads with incompatible batching, locality, and tail-latency requirements. TransX therefore disaggregates serving into three stages: bulk state construction, nearline incremental maintenance, and online prediction.
