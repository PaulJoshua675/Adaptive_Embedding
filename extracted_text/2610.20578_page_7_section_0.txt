But as we created and helped users create SquashFS images, we found great discrepancies with the time it took to create them. Hence, we designed experiments to benchmark eleven common user workflows by measuring the SquashFS creation execution time using both the central file system and local compute node storage. Our work led to several recommenda- tions for creating SquashFS images on HPC systems. First, if a file arrives already compressed then create the SquashFS image directly from the compressed file; do not uncompress it. If it arrives as files-and-directories, compress the dataset into a tar.gz file before creating the SquashFS image. But if there is a need to expand a compressed file and if there is access to local storage on the SSDs or HDDs, it is more advantageous to copy and expand the dataset on the local storage. However, while there is some performance improvement on SDD local storage, it is only a marginal improvement in performance over HDD local storage and not enough to warrant recommendation of one over another. These results and recommendations led to follow up ques- tions that will be addressed in future work. For example, we would like to investigate the decline in performance for datasets with high inode counts when using a high thread count for SquashFS image creation. We would like to investigate the SquashFS performance as a function of inodes. And once the SquashFS image is created, to benchmark the performance of common workflows.
