Gemini 3.1 Pro is the prover backbone in the reported experiments. The implementation requests temperature zero for proof generation, query generation, and the reasoning-controller calls. Each revision is conditioned on the current candidate, latest diagnostic, and available retrieval and failure-memory context, maintaining a single proof trajectory. Verification and proof-hole integrity. The Lean verifier uses lean-interact with a Mathlib environment, with v4.28.0-rc1 as the fallback toolchain version. Its default timeout is 600 seconds per verification call. The integrity-aware path isolates one target proof hole and preserves the surrounding source as an immutable prefix and suffix. The model returns a tactic body, which the host inserts into this source. Before compilation, the checker rejects changes to the protected context, additional top-level commands, and prohibited constructs such as sorry, admit, and newly introduced axiom declarations. The checks ignore comments and string contents. Under this contract, success requires both valid source boundaries and successful Lean elaboration without unresolved sorry obligations. Reflection budgets. The implementation records the initial attempt at round zero and subsequent revisions with increasing round indices. The reported evaluation measures cumulative completion at budgets k ∈{8, 16, 32}. Proof-generation calls, retrieval actions, and compiler submissions are tracked separately in the budgeted controller. One retrieval action can issue several search queries, while initial reasoning preparation has its own planning budget. These counters also distinguish a newly compiled candidate from an exact failed candidate rejected using cached feedback. Failure memory. Memory is initialized separately for each proving problem and is not used in the standalone mathematical retrieval benchmarks. For a stable failed candidate, the implementation serializes its error category, normalized diagnostic, unresolved goals, local context, inferred failing tactic, referenced identifiers, and nearby source snippet. A SHA-256 hash identifies the state, and the record stores its occurrence count and associated unsuccessful edits (NIST, 2015). The repeat threshold is two observations. Feedback includes at most three recurrent states and the three most recent failed edits for each, together with a directive to change the unsuccessful repair. When memory is enabled, the FAILURE MEMORY GUIDANCE STRICT instruction is included in the initial proof prompt and every proof-refinement prompt. The structured failure memory summary is appended to compiler-tool feedback, so both the proof-refinement prompt and the reflection-query prompt receive it.
