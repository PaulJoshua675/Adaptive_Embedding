Unless otherwise stated, we compare against the baseline production recommendation stack under matched data and product constraints. 8.1 Deployment Setting and Evaluation Protocol Production setting. We deploy TransX in a large-scale social recommendation application with long, heterogeneous user histories and highly variable candidate fanout, ranging from approximately 0.5K to 1.2K candidates per request. The system serves on the order of 20K requests per second and processes hundreds of millions of user interactions per day under strict latency and infrastructure-cost constraints. Online model scoring runs primarily on an H200 GPU serving fleet and is subject to a p99 end-to-end scoring-latency SLO of less than 50 ms. Historical behavior is constructed over a 180-day lookback window, allowing the behavior encoder to exploit substantially longer context than the short-history features typically exposed to conventional ranking models. As described in Section 5.3, a fallback DLRM (Naumov et al., 2019) is co-deployed to serve requests for which no valid KV cache can be retrieved. The deployed system follows the same disaggregated serving design. Bulk and nearline workers maintain behavioral state and publish compact behavior memory KV snapshots, while online workers perform only candidate-conditioned readout and prediction. This separation makes both model quality and infrastructure efficiency first-class deployment criteria. Models are retrained and freshly deployed daily, with an end-to-end refresh SLO requiring training, bulk prefill, and production rollout to complete within 20 hours. Nearline state maintenance is subject to a p90 freshness-lag SLO of 2 seconds, aligned with the system’s typical pagination interval. Production reference. For each TransX ramp, the control is the incumbent model currently serving the same recommendation product surface, so the reported gains measure the production transition rather than a comparison against an offline or simplified baseline. For the click/conversion prediction task on the primary landing and home-page surfaces, the control is the production HSTU-style (Zhai et al., 2024) sequential recommender, trained over a 180-day behavioral lookback window (capped at 512 tokens) using our production configuration. This control performs history encoding and candidate scoring entirely on the online serving path. For retrieval, the control is a sequential embedding-based retrieval (EBR) model whose user tower encodes up to 180 days of behavioral history (capped at 1024 tokens) with Transformer blocks. The user and item towers map into a shared 128-dimensional embedding space, and the resulting representations are used by an ANN service to retrieve the top-200 candidates, which are merged with candidates from other retrieval sources before downstream ranking. For the slate-ranking task used on notification and email surfaces, the control is a production DLRM-based learning-to-rank model (LtR DLRM) (Borisyuk et al., 2024) in which behavioral history is represented through engineered aggregate and sequence-derived features and scored entirely online. Accordingly, the emphasis of this technical report is the production transition from established serving systems to TransX—including quality, efficiency, and operational behavior—rather than leaderboard-style benchmarking against generic reference models. Offline protocol. We construct the offline dataset from up to one year of historical user behavior and 180 days of event-level feedback, choosing the terminal date sufficiently far in the past for delayed feedback to have fully matured. For each user trajectory, the behavioral sequence contains up to the preceding 180 days of activity, capped at 8192 tokens. For each packed training unit, supervised events within that unit share its left boundary and differ only in their causal right-hand cutoffs. Training, validation, and test sets are split chronologically, with the validation and test sets each spanning one week.
