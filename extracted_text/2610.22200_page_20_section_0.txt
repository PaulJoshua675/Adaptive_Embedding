These decisions are expressed as Python programs against a common SDK, allowing device operations and programmatic checks to share the same control flow. Runtime. The runtime manages the agent loop and executes programs in a persistent interpreter. Variables, imports, and the working directory persist across turns, supporting incremental execution. It collects execution feedback and explicitly emitted observations, applies the configured context-retention policies, and constructs the next model input. Device SDK. The SDK binds observations and actions to explicit resources, such as devices, windows, and browser tabs (Section 4.2). Short element IDs written directly by the model must originate from observations delivered to it; programs may also obtain element references from fresh observations and use them within the same execution. Resource resets or rebinding invalidate associated references. These constraints establish the provenance and scope of action targets, but do not guarantee that the interface remains unchanged before execution. Driver. The driver translates SDK requests into supported native operations, including accessibility actions and coordinate-based input. It manages element identities and snapshot metadata, selects action- delivery mechanisms, and applies foreground or background delivery policies. Detectable native failures are returned as typed errors so that the agent can distinguish execution failures from outcomes requiring further inspection. Applications and Operating System. Applications and the operating system determine the available observations and control capabilities. Permissions, application state, and accessibility support constrain which operations can be performed. The harness must expose these limitations and use alternative interaction methods where supported. 4.3.2 Responding to Real-Device Challenges The constraints discussed in Section 4.1 motivate four design choices that connect these layers. Minimizing Interference on Shared Machines. An agent operating alongside a user cannot assume exclusive control of the pointer, keyboard, or focused window. The harness therefore prefers element- level accessibility actions, followed by window-targeted coordinate input, and finally foreground input. Background delivery is used only where the target and platform support it; window-relative coordinates alone do not imply background execution. When a less intrusive method is unavailable or ineffective, the agent can escalate to a supported alternative, coordinating with the user before foreground input. 20
