Inductor’s performance benefits are largely rooted in NVIDIA-specific optimizations refined over years of devel- opment and iterative tuning. Porting to alternative accelera- tors, such as AMD GPUs, necessitates more than mechanical adaptation; it requires re-evaluating core heuristics, expanding autotuning search spaces, and developing bespoke micro- architecture aware optimizations. 1) Optimization Techniques: We apply AMD-specific opti- mizations leveraging architectural insights from Section IV-A: Software pipelining. We replace Python range() with Triton’s tl.range() using num_stages=2, enabling better memory- compute overlap. This reduces latency by 11.7% for ResNet-50 reduction kernels. Native Triton intrinsics are used to replace library function calls where available: tl.rsqrt() instead of libdevice.rsqrt(), and tl.minimum / tl.maximum instead of helper functions. Register configuration. With 256 vector general purpose registers (VGPRs) per thread, we raise Inductor’s register spill threshold from 16 to 32 for larger tiles and better instruction- level parallelism. Expanded autotuning. We extend Inductor’s autotuning config- urations with AMD-specific tile sizes and occupancy hints. For example, we add non-square tiles (64 × 32, 128 × 16, 128 × 32, 32 × 512) for 2D pointwise kernels. 2) Model-Level Results: We evaluate these optimizations on standard vision and language models. Fig. 13 shows per- category kernel latencies for three models trained on MI350X before/after optimization versus B200. For ResNet-50 [51], reduction kernels improve 11.7%, reaching 1.16× of B200 latency; other Triton inductor kernels outperform B200. For DenseNet-121 [52], pointwise kernels improve 9.2%; reduction improves 6.9%, reaching B200 parity; persistent reduction improves 3.5%. Overall kernel time is reduced by 4.2%. For NanoGPT [53], persistent reduction improves 4.8%; pointwise improves 3.8%. Overall kernel time is reduced by 3.4%. In summary, AMD-specific optimizations deliver 6.9–11.7% improvement for reduction, 3.5–4.8% for persistent reduction, and up to 9.2% for pointwise. While MI350X matches or exceeds B200 across several categories for CNNs, it is still 30% slower on transformer Inductor kernels, indicating optimization headroom remains. V. MODEL-SYSTEM CO-DESIGN AMD MI350X’s large HBM capacity creates opportunities for model-system co-design, where training configurations and model architectures are jointly optimized to exploit the additional memory resources. We explore two complementary directions: improving training throughput (examples/second) and improving model quality. A. Strategies for Training Efficiency Increased batch size. Larger HBM capacity enables training with larger batch sizes, improving GPU utilization by amortizing kernel launch overhead and better saturating compute units. For example, a friend recommendation model achieves 26% speedup at 2× batch size, 46% at 4×, and 51% at 6× (Fig. 15a). For a social ranking model migrated to MI350X, doubling the batch size yields 12–15% throughput improvement over B200 baseline with the same batch size (B200 encounters out-of- memory errors at doubled batch size). Removal of activation checkpointing. Activation check- pointing (AC) trades memory for computation by recomput- ing activations during the backward pass instead of storing them. With larger HBM, AC can be disabled for memory- constrained layers, eliminating redundant recomputation. The activation memory budget controls how aggressively PyTorch checkpoints activations: a budget of 1.0 saves all activations (maximum memory, no recomputation), while lower values trigger selective recomputation to reduce memory at the cost of throughput. Fig. 14 shows the tradeoff between activation memory budget and training throughput on a 1.3B-parameter GPT model. MI350X’s larger HBM enables it to run without AC entirely, achieving 96.4 examples/second. In contrast, B200 must use aggressive AC (budget ≤0.35) just to fit, achieving 71.5 examples/second, a 1.35× throughput disadvantage solely attributable to memory constraints. Dense parallelism strategy tuning. Additional HBM allows for relaxed sharding strategies, mitigating communication overhead. For FSDP-based training [54], moving from ZeRO-3 to ZeRO- 2 or ZeRO-1 [55] reduces AllGather and ReduceScatter communication volume. Switching to HSDP (Hybrid Sharded Data Parallelism) further hides communication latency by overlapping with computation. For a large Ads foundation model at 1K GPU scale, HSDP provides 6% speedup at the cost of 750 MB additional memory per GPU, a tradeoff feasible only with HBM capacity headroom.
