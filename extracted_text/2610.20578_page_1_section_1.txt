Modern high performance computing (HPC) systems re- quire high performance parallel storage arrays to process large datasets effectively. These parallel storage arrays are designed to read and write tens to hundreds of gigabytes or more of data per second in order to keep up with the processing capabilities of the compute nodes. They work best for reasonably large files (> 10s of megabytes per file). With the growth of data science and machine learning applications on HPC systems it is not unusual to see input datasets that are comprised of hundreds of thousands to millions of small files. The instances, where there are hundreds of thousands to millions of small file accesses coming from many compute nodes, generate tremendous load on the metadata servers of the parallel storage array, adversely affecting all of the users on the HPC system. In general, data science and machine learning workflows involve downloading these datasets to a local system because accessing them over the Internet as the workflow is executing incurs far too much latency to be effective. The datasets are made available in one of a number of formats including tar.gz, zip, tfrecords, HDF5, and/or direct files-and-directories. (The latter is particularly prevalent when the dataset is assembled from data files being downloaded from across the Internet.) As researchers, scientists, and engineers, the first inclination is to uncompress the downloaded file and work with the dataset as directories and files on the central file system. However, while the dataset may be far below the capacity quota for an individual account on the central storage, it could easily be above into the inode quota for a user account. In such cases, what guidance needs to be provided so that the data processing is efficient for the researcher while not adversely impacting the rest of the computing community? Over the past several years, members of the Lincoln Labo- ratory Supercomputing Center have been encouraging users with high-inode-count, read-only datasets to compact them into SquashFS images, which are subsequently mounted on a local loopback device for read-only access. The SquashFS images have some inherent advantages over FUSE-mounted compressed file system images and they solve the issue of storing multimillion-inode datasets as files and directories natively on disk. In this paper, we present the results of a benchmark study that compares numerous workflows for creating SquashFS images from a downloaded dataset.
