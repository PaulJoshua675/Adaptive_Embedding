HTN-Orchestrate dispatch - Send agents when R does not yet fully + verifiably answer the leaf task. Pursue important routes through genuinely different retrieval methods. Verify BEFORE finishing: once you have a candidate, dispatch a verifier so it re-confirms with independent searches. wait - Use when R is not sufficient to terminate, at least one agent is still in flight, and R exposes no distinct gap worth dispatching. terminate - When R contains a complete answer AND a verifier has confirmed it, OR when no distinct evidence-producing route remains. Retain the best-supported candidate and explicit unresolved gaps. Each dispatch call specifies role_id, task_summary, and rationale. Multiple dispatch calls in one response start independent assignments concurrently. Researcher. The Researcher receives a self-contained assignment produced by the instruction generator. The system prompt specifies a five-step methodology (understand, search strategically, extract with precision, compute and ver- ify in code, write a complete answer) and requires all calculations to use Python. The report is submitted through a submit_report(content, confidence) tool call: Scope: [what was investigated] Finding: [best-supported finding or ranked candidates] Constraint ledger: [candidate] - SUPPORTED / CONTRADICTED / UNRESOLVED for each constraint Evidence: Source URL or computation Confidence: [numeric value from 0.0 to 1.0] Conflicts: [contradictions between sources with citations, or "none"] Verifier. The Verifier receives the proposed answer, the original task, and supporting reports. Its system prompt specifies four phases: (1) completeness, listing every requirement as answered or missing; (2) correctness, independently verifying factual claims and recomputing calculations; (3) precision, confirming exact values rather than approximations; and (4) answer contract, checking scope and format. Its report uses: Verdict: CONFIRMED | NEEDS CORRECTION | INCOMPLETE Unconfirmed or wrong constraints: [specific factual gaps, or "none"] Corrected answer: [supported replacement, or "N/A"] Synthesis. Separate templates cover leaf, internal-node, and root synthesis. Leaf synthesis joins worker reports into an evidence memo. Internal synthesis combines child results for the parent. Root synthesis checks every requested output field and returns the final answer. All templates distinguish resolved (the complete answer-bearing claim is positively supported) from exhausted_unresolved (a decisive relation remains missing after available routes are exhausted, with partial evidence preserved). Recovery. When the current task network cannot resolve the root objective, the recovery step extracts supported facts through an extract_supported_facts tool that requires each claim to include a verbatim supporting quote and source reference. These facts, together with unresolved relations and the reason the previous approach stopped, form the restart context for the next epoch. The rebuild instructions supplement the Planner with the requirement to identify the most discriminative unresolved relation and to preserve a discovery route that can surface an alternative candidate. C. Additional Results and Ablation Details C.1. Ablation Definitions All three ablations use the same 200 BrowseComp questions. Each changes one part of the orchestration procedure while preserving the remaining mechanisms. In the single-agent variant, the unit of assignment is an executed leaf within an epoch. A question may still contain several leaves, and a rebuilt task network may introduce new leaves. In the upfront variant, a downstream worker can consume completed prerequisite results even though its position and objective were planned earlier. 17
